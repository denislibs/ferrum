# Ferrum — подсистема 1: ядро редактора

Дата: 2026-10-23 · Статус: на ревью

## 1. Контекст

Ferrum — векторный редактор для дизайна интерфейсов, аналог Figma. Ядро на Rust, интерфейс на SolidJS + TypeScript. Работает в браузере и как десктопное приложение (Tauri v2) из одной кодовой базы.

Проект разбит на подсистемы, у каждой свой цикл «спека → план → реализация»:

| № | Подсистема | Содержание |
|---|---|---|
| 1 | **Ядро редактора** (этот документ) | модель документа, рендер, холст, инструменты фигур, выделение, undo/redo, файлы, минимальный интерфейс |
| 2 | Оболочка редактора | контекстные меню, палитра команд, полировка панелей |
| 3 | Векторы и текст | pen tool, векторные сети, булевы операции, текстовый движок, стрелка, Scale (K), экспорт SVG/PDF |
| 4 | Бэкенд и совместная работа | аккаунты, сервер, синхронизация Loro, курсоры, офлайн, серверное хранилище `.ferrum` |
| 5 | Дизайн-системы | auto layout, компоненты, варианты, переменные, стили, вкладка «Ассеты» |
| 6 | Прототипирование, плагины, Dev Mode | |
| 7 | Импорт из Figma (последней) | чтение `.fig` (формат Kiwi) как основной путь, Figma REST API как запасной; вставка из буфера обмена Figma |

Визуальный язык интерфейса задан дизайн-системой Ferrum: https://claude.ai/artifact/L9ZDGW6XCRGquBLYTtYYUK

Разработка: код пишет в основном Claude, автор проекта направляет и проверяет. Ключевые решения поясняются в коде и описаниях шагов.

## 2. Цели и не-цели

**В подсистеме 1 пользователь может:**
- создавать, открывать и сохранять файлы `.ferrum` (диск в Tauri; IndexedDB и File System Access в браузере);
- работать с несколькими страницами;
- рисовать фреймы (с пресетами размеров), прямоугольники, эллипсы, линии, группы, размещать изображения;
- выделять, перемещать, менять размер и поворачивать объекты, менять порядок и вложенность;
- задавать заливки (цвет, изображение), обводки, прозрачность, радиус скругления, обрезку содержимого фрейма;
- отменять и повторять действия;
- зумить от 2% до 25 600% и панорамировать бесконечный холст;
- экспортировать фрейм или выделение в PNG @1x/@2x/@3x;
- переназначать горячие клавиши.

**Не входит:** текст, pen tool, булевы операции, SVG/PDF-экспорт (подсистема 3); сервер и совместная работа (4); auto layout и компоненты (5); прототипы (6); импорт Figma (7); подсказки расстояний между объектами и измерение с Alt (позже).

## 3. Цели производительности

- Страница на 100 000 узлов открывается быстрее 2 с.
- Зум и панорамирование — 60+ fps на странице в 100 000 узлов.
- Перетаскивание 1000 выделенных объектов без просадки кадров.
- Интерфейс панелей не блокируется работой ядра.

Модель документа проверена бенчмарком до начала реализации (прототип, 2026-10-23). Наивная реализация на Loro не проходила цели: открытие 100 000 узлов — 4.6 с, файл — 44 МБ, undo — 818 мс, память при первом undo — ~550 МБ. Решения в разделе 5 (стабильные ID, значения вместо контейнеров, зеркало свойств, кэш сцены, shallow-снапшот, своя история отмены) приводят к целям этапа 1, которые контрольный бенчмарк `bench_report` проверяет на странице из 100 000 узлов (нативно, release; WASM ожидается в 1.5–2 раза медленнее):

| Метрика | Цель | Замер прототипа |
|---|---|---|
| Открытие до первого кадра (из кэша сцены) | ≤ 300 мс | 55 мс |
| Фоновая загрузка Loro | ≤ 1500 мс | 304 мс |
| Память открытого документа | ≤ 400 МБ | 149 МБ |
| Размер файла | ≤ 30 МБ | 26.6 МБ |
| Правка свойства | ≤ 1 мс | 0.01 мс |
| Undo одной правки / сдвига 1000 узлов | ≤ 50 мс | 0.0 / 1.3 мс |
| Сдвиг 1000 узлов одной транзакцией | ≤ 50 мс | 6.9 мс |
| Полное сохранение | ≤ 1500 мс | 780 мс |

Для 500 000 узлов (справочно): первый кадр — 0.38 с, фоновая загрузка — 2 с, память — 865 МБ, полное сохранение — 4.5 с. Полное сохранение такого размера блокирует worker, поэтому автосохранение пишет только инкрементальные обновления (раздел 10).

## 4. Архитектура

### 4.1 Репозиторий

```
ferrum/
├─ crates/                 Cargo workspace
│  ├─ ferrum-doc           модель документа на Loro: схема, мутации, undo/redo, формат .ferrum
│  ├─ ferrum-scene         производный кэш: мировые трансформы, bounds, R-tree (rstar)
│  ├─ ferrum-render        vello: сборка кадра, камера, оверлеи, кэши, экспорт PNG
│  ├─ ferrum-editor        инструменты, выделение, ввод, привязки, таблица команд, раскладка клавиш
│  └─ ferrum-wasm          wasm-bindgen: протокол обмена с основным потоком
└─ apps/
   ├─ web                  Vite + SolidJS + TypeScript
   └─ desktop              Tauri v2, оборачивает сборку apps/web
```

Границы крейтов:
- `ferrum-doc` не знает о рендере; остальные крейты не видят Loro напрямую, только API `ferrum-doc`.
- `ferrum-render` не знает о Loro и инструментах; получает сцену, камеру и описание оверлеев.
- `ferrum-editor` не зависит от браузера и тестируется обычным `cargo test`.

### 4.2 Потоки

```
Основной поток (Solid)                    Web Worker (Rust/WASM)
<canvas> → transferControlToOffscreen ──→ OffscreenCanvas + vello
ввод (SAB-буфер) ───────────────────────→ ferrum-editor → doc → scene → render
живое состояние (SAB) ←───────────────── X/Y/W/H выделения, камера, статистика кадра
команды (postMessage) ──────────────────→
события (postMessage) ←───────────────── выделение, структура слоёв, курсор, ошибки
буфер обмена, диалоги файлов ←─────────→ запросы/ответы, байты как transferable
```

Ядро с первого дня работает в выделенном Web Worker с OffscreenCanvas.

### 4.3 Протокол обмена

- **SharedArrayBuffer** для потоков каждого кадра:
  - кольцевой буфер ввода: pointer (с `getCoalescedEvents()`), wheel, key; worker вычитывает накопленное в начале кадра;
  - блок живого состояния: значения выделения во время перетаскивания, камера, зум, статистика кадра; основной поток читает его в rAF в фазе measure;
  - синхронизация через `Atomics`: счётчики версий, флаг новых данных, счётчик кадров.
- **postMessage** для команд и событий. Типы сообщений описаны в Rust, TypeScript-типы генерируются `tsify`.
- Байты файлов и изображений передаются transferable `ArrayBuffer`.
- Весь обмен идёт через интерфейс `Transport`. При `crossOriginIsolated === false` автоматически используется реализация только на postMessage.
- Требуются заголовки `Cross-Origin-Opener-Policy: same-origin` и `Cross-Origin-Embedder-Policy: credentialless` в Vite, на хостинге и в Tauri. Следствие для подсистемы 4: вход через OAuth делается редиректом, не попапом.
- Многопоточный WASM (`wasm-bindgen-rayon`, nightly Rust) заложен как возможность и включается по результатам бенчмарка.

### 4.4 Планировщик интерфейса

Собственная реализация идей fasterdom (код Telegram Web A не используется: он под GPL-3.0):
- события из worker'а, пришедшие между кадрами, применяются к сигналам Solid один раз за rAF в одном `batch()`;
- фазы `measure` (чтения layout) и `mutate` (ручные записи в DOM) в каждом кадре;
- в dev-режиме предупреждение при чтении layout вне фазы `measure`.

## 5. Модель документа (`ferrum-doc`)

### 5.1 Структура

- **Корневой LoroDoc:** `meta` (`schemaVersion`, имя файла), упорядоченный список страниц (id, имя). В подсистеме 5 здесь появятся компоненты.
- **Один LoroDoc на страницу:** `LoroTree` узлов страницы. Загружается только открытая страница, остальные — по требованию.
- Перенос узлов между страницами выполняется как копирование + удаление; отменяется двумя шагами.

### 5.2 Узлы

- **Стабильный ID узла** (`NodeId`) — `TreeID` его первого создания, записанный ключом `id` в свойства узла. Loro при восстановлении удалённого узла выдаёт ему новый `TreeID`, но копирует свойства, поэтому `NodeId` переживает undo/redo и перезагрузку. Страница держит индекс «`NodeId` → текущий `TreeID`». Порядок детей — дробные индексы Loro.
- Типы: `frame`, `group`, `rect`, `ellipse`, `line`, `image`. Новые типы добавляются без миграции старых файлов.
- Каждое свойство — отдельный ключ в `LoroMap` узла: `id, type, name, x, y, w, h, rotation, opacity, visible, locked, cornerRadius, clipContent, fills, strokes`.
- **Нейтральные значения не записываются:** `x`, `y`, `rotation`, `cornerRadius` = 0, `opacity` = 1, `visible` = true, `locked` = false подставляются при чтении. Поэтому нейтральные значения по умолчанию в схеме менять нельзя.
- Координаты `f64` в пикселях, относительно родителя. Линия: длина `w`, `h = 0`, поворот. Группа хранит `x`, `y`, `rotation`, но не `w`/`h`: её границы вычисляются по детям. Перемещение группы меняет только её `x`/`y`; ресайз группы масштабирует геометрию детей в одной транзакции.
- `fills`: неизменяемое значение-список (не контейнер Loro) из `{ kind: solid | image, color: "#rrggbbaa", imageHash, scaleMode: fill | fit | tile, opacity, visible }`, снизу вверх; заменяется целиком. Контейнер на каждую заливку раздувал файл почти втрое.
- `strokes`: такое же значение-список из `{ color, width, align: inside | center | outside }`.

### 5.3 Зеркало свойств и кэш сцены

- Чтение свойства из Loro стоит ~9 мкс на узел. Страница держит **зеркало свойств** всех живых узлов в памяти: наши правки обновляют его напрямую, загрузка без кэша заполняет его один раз из Loro. `props()`, кэш сцены и ссылки на изображения читаются из зеркала.
- **Кэш сцены** — плоская таблица всех узлов страницы (стабильный ID, текущий `TreeID`, индекс родителя, все свойства) в порядке обхода. Пишется в файл при каждом сохранении вместе с хэшем снапшота, из которого построен.
- **Открытие файла:** таблица читается сразу (55 мс на 100 000 узлов), и холст рисуется по ней. Loro раскодируется в фоне внутри worker'а; индекс и зеркало берутся из таблицы без чтения Loro. До окончания фоновой загрузки правки недоступны. Если хэш не совпал или таблица повреждена, кэш молча игнорируется и страница загружается из Loro.
- Подсистема 4 (импорт чужих правок) добавит обновление зеркала и индекса по событиям Loro для изменённых узлов.

### 5.4 Изображения и формат `.ferrum`

- Байты изображений не хранятся в Loro; узел ссылается на хэш blake3.
- Контейнер `.ferrum`: `magic "FERRUM\0\0" · версия формата · секции`. Секция: `тип · id · длина · blake3(данных) · данные`. Типы: корневой документ, shallow-снапшот страницы, ссылки страницы на изображения, изображение по хэшу, кэш сцены страницы. Повреждённая секция пропускается с предупреждением; неизвестные типы секций (из будущих версий) пропускаются.
- Страницы сохраняются **shallow-снапшотом** Loro — текущее состояние без истории правок: он на треть меньше полного, быстрее раскодируется и для документа после правок быстрее экспортируется. История между сессиями не нужна: отмена работает в пределах сессии, версии файла появятся с сервером.
- Неиспользуемые изображения не записываются.
- `meta.schemaVersion` + цепочка миграций при открытии старых файлов. Файл более новой версии открывается только для чтения с предупреждением.
- Loro зафиксирован на 1.16.2 вместе с `loro-internal` 1.16.2: с `loro-internal` 1.17 эта версия не собирается.

### 5.5 Транзакции и история

- API: `create_node`, `set_props(id, patch)`, `move_node(id, parent, index)`, `delete_nodes`, `Document::transact(page, selection, |page| …)`.
- **Своя история отмены, без `UndoManager` Loro.** Первый undo через `UndoManager` на 100 000 узлах стоил 0.35–0.75 с и ~450 МБ памяти (Loro строит внутренние структуры на весь документ). Вместо этого каждая правка записывает в журнал транзакции обратную операцию: для изменения свойств — прежние значения изменённых полей (из зеркала), для создания — удаление, для удаления — восстановление поддерева с прежними `NodeId`, для перемещения — возврат на прежнее место. Undo применяет обратные операции и записывает их собственные обратные для redo. Память растёт с числом правок, а не с размером документа. Отмена создаёт новые операции Loro и отменяет только свои правки — так же, как `UndoManager`.
- Глобальный стек хранит шаги всех страниц в порядке действий пользователя. Одно действие (например, от нажатия до отпускания мыши) — один шаг; транзакция без изменений шага не создаёт. При ошибке внутри транзакции её изменения откатываются обратными операциями.
- Выделение не хранится в документе, но сохраняется в шаге и восстанавливается при undo/redo.
- Во время перетаскивания, ресайза и поворота изменения живут только как временное превью в `ferrum-scene`; в Loro записывается одна транзакция при отпускании. В подсистеме 4 живое превью для других участников пойдёт через `EphemeralStore`.

## 6. Сцена (`ferrum-scene`)

- Производный кэш из документа: мировые трансформы, bounds в мировых координатах, R-tree для отсечения и hit-testing.
- При открытии файла строится из кэша сцены (раздел 5.3), до загрузки Loro. Дальше обновляется по изменениям документа, пересчитывая только затронутые узлы и их предков (для bounds групп).
- Слой временного превью поверх документа для текущего жеста.

## 7. Редактор (`ferrum-editor`)

### 7.1 Инструменты

Трейт `Tool`: `pointer_down / move / up`, `key`, `cancel`, `cursor()`, `overlay()`.

| Инструмент | Клавиша | Назначение |
|---|---|---|
| Перемещение | V | выделение, перемещение, ресайз, поворот |
| Фрейм | F, A | рисование фрейма; пресеты размеров |
| Прямоугольник / Эллипс / Линия | R / O / L | рисование фигур |
| Рука | H, удержание Space | панорамирование |
| Изображение | Ctrl/Cmd+Shift+K, вставка, перетаскивание файла | размещение изображения |

Инструмент «Перемещение»: состояния `Idle → Pressed → Dragging | Marquee | Resizing(handle) | Rotating`; перетаскивание начинается после 3px; поворот — курсор чуть за угловой ручкой.

### 7.2 Выделение

- Клик выбирает объект верхнего уровня внутри фрейма; двойной клик — на уровень глубже; Ctrl/Cmd+клик — самый глубокий объект.
- Shift+клик добавляет или убирает объект. Рамка выделения выбирает пересекаемые объекты.
- Перетаскивание во фрейм делает объект его ребёнком, вытаскивание — убирает из фрейма.

### 7.3 Модификаторы и привязки

- Shift: пропорции, движение по оси, поворот шагом 15°. Alt: ресайз от центра; Alt+перетаскивание — дубликат.
- Привязка к краям и центрам соседних объектов и родительского фрейма, порог 4 экранных пикселя, красные линии-подсказки.
- Привязка к целым пикселям включена по умолчанию, отключается в настройках.

### 7.4 Hit-testing

R-tree отбирает кандидатов по bounds, затем точная проверка геометрии kurbo с учётом поворота и толщины обводки. Допуск для тонких линий — 4 экранных пикселя.

### 7.5 Пресеты фреймов

Отдельный JSON-файл со списком, по умолчанию: iPhone 16 (393×852), iPhone 16 Pro Max (440×956), Android Compact (412×917), iPad mini (744×1133), iPad Pro 11" (834×1194), Desktop (1440×1024), MacBook Air (1280×832), 1920×1080, Instagram post (1080×1350), Story (1080×1920), A4 (595×842). Список дополняется без изменения кода.

### 7.6 Команды и горячие клавиши

- Единая таблица команд в Rust; меню интерфейса вызывают команды по ID.
- Раскладка по умолчанию повторяет Figma, с вариантами Cmd (macOS) и Ctrl (Windows/Linux). Основные сочетания: Delete; Ctrl+D; Ctrl+G / Ctrl+Shift+G; Ctrl+Alt+G; Ctrl+] / Ctrl+[ (с Alt — на передний/задний план); стрелки 1px, Shift+стрелки 10px; Shift+1 (показать всё), Shift+2 (к выделению), Shift+0 (100%); Ctrl+Shift+H (скрыть/показать); Ctrl+Shift+L (заблокировать); Ctrl+\ (скрыть интерфейс); Ctrl+C / Ctrl+V / Ctrl+X; Ctrl+Shift+C (копировать как PNG); Ctrl+Z / Ctrl+Shift+Z. При реализации таблица сверяется с официальным списком горячих клавиш Figma.
- **Переназначение:** экран настроек с поиском; хранятся только отличия от раскладки по умолчанию; обнаружение конфликтов с предложением заменить; сброс одной команды или всех; импорт и экспорт JSON.
- Буквенные клавиши сопоставляются по `KeyboardEvent.code`, поэтому работают на любой раскладке (включая русскую). Подписи показываются для текущей раскладки через `navigator.keyboard.getLayoutMap()`, где доступно.
- В веб-версии сочетания, которые перехватывает браузер (Ctrl+W, Ctrl+T, Ctrl+N и т. п.), помечаются предупреждением; в Tauri доступны все.
- Если фокус в поле ввода панели, клавиши обрабатывает интерфейс.
- Настройки хранятся у пользователя (IndexedDB в браузере, файл конфигурации в Tauri), не в документе.

### 7.7 Буфер обмена

- Ctrl+C кладёт формат `web application/x-ferrum` (поддерево узлов + изображения).
- Ctrl+Shift+C — копирование как PNG.
- Вставка изображений из системного буфера.

### 7.8 Путь события

SAB-буфер ввода → worker в начале кадра обрабатывает события по порядку → инструмент обновляет превью в сцене → при отпускании изменения записываются в Loro одной транзакцией (один шаг undo).

## 8. Рендер (`ferrum-render`)

### 8.1 Бэкенд

vello + wgpu (WebGPU) в OffscreenCanvas. Запасные варианты, выбираемые автоматически при старте: `vello_hybrid` (WebGL2), затем `vello_cpu`. Десктоп в первой версии использует тот же путь, что и браузер.

### 8.2 Цикл кадров

Основной поток в `requestAnimationFrame` увеличивает счётчик кадров в SAB и вызывает `Atomics.notify`; worker ждёт в `Atomics.waitAsync`. Кадр рисуется только при изменении сцены, камеры или оверлея.

### 8.3 Камера и точность

- Центр в `f64`, зум 0.02–256, зум колесом к курсору, щипок тачпада (Ctrl+wheel).
- Перед отправкой на GPU координаты переводятся в систему относительно камеры и затем в `f32` — без дрожания на больших координатах.
- `devicePixelRatio` учитывается; размер канваса отслеживает `ResizeObserver` в основном потоке и передаёт через SAB.

### 8.4 Сборка кадра

1. Отсечение невидимого через R-tree.
2. Кэш фрагментов: каждый узел кодируется в собственный `vello::Scene` в локальных координатах; кадр — склейка фрагментов с матрицами. Правка узла сбрасывает только его фрагмент.
3. LOD: объекты меньше 0.5px не рисуются; мелкие — прямоугольником цвета первой заливки.
4. Растровый кэш фреймов верхнего уровня при сильном отдалении — включается, если бенчмарк покажет необходимость.

### 8.5 Фреймы, прозрачность, изображения, цвет

- `clipContent` → слой vello с маской.
- `opacity < 1` у контейнера → слой; у листовой фигуры прозрачность умножается в цвет.
- Изображения: `createImageBitmap` в worker'е → текстура; уменьшенные версии под текущий зум; бюджет GPU-памяти с LRU-вытеснением.
- Цвет sRGB. Display P3 — позже.

### 8.6 Оверлеи

В той же сцене vello поверх содержимого, в экранных пикселях: рамки выделения, ручки (8px), подсветка наведения, рамка выделения мышью, линии привязки, пиксельная сетка (зум ≥ 800%), названия фреймов, бейдж «W × H». Подписи — однострочный текст через `parley` со встроенным шрифтом Onest.

### 8.7 Экспорт

PNG фрейма или выделения в @1x/@2x/@3x тем же рендером в отдельную текстуру; размер пиксель в пиксель (фрейм 393×852 @3x → 1179×2556).

## 9. Интерфейс (apps/web)

Раскладка как в Figma UI3; внешний вид — дизайн-система Ferrum (свои цвета, иконки, шрифт).

- **Левая панель:** меню и имя файла; страницы (сворачиваемые); дерево слоёв — виртуализировано (основной поток запрашивает у worker'а только видимые строки), переименование на месте, перетаскивание для порядка и вложенности, скрыть и заблокировать.
- **Нижний плавающий тулбар по центру:** перемещение, фрейм, фигуры (выпадающий список: прямоугольник, эллипс, линия, изображение). Места под перо, текст, комментарии зарезервированы.
- **Правая панель:** сверху «Поделиться» (неактивна до подсистемы 4) и зум; вкладки «Дизайн» и «Прототип» (вторая неактивна). Секции «Дизайн»: Фрейм/Положение (пресеты, X/Y/W/H, поворот) → Вид (прозрачность, радиус, обрезка) → Заливка → Обводка → Экспорт. Без выделения — цвет фона страницы и экспорт.
- **Палитра цвета:** HSB, HEX, прозрачность, пипетка (`EyeDropper` API, где доступен).
- **Настройки:** горячие клавиши, тема (тёмная / светлая / системная), привязка к пикселям.
- **Экран файлов:** недавние, создать, открыть, импорт `.ferrum`.
- Ctrl+\ скрывает интерфейс; ширина панелей меняется перетаскиванием края.

Дизайн-система обновляется под эту раскладку: компонент Toolbar переделывается в нижний плавающий, добавляются шапки панелей.

## 10. Хранение файлов

- Интерфейс `FileStore` (TypeScript) с реализациями: IndexedDB (браузер), File System Access API (Chrome/Edge), Tauri (диск). Серверное хранилище добавится в подсистеме 4 как ещё одна реализация того же формата.
- Автосохранение через 2 с после последней правки: инкрементальные обновления Loro в журнал (миллисекунды). Полное сохранение (shallow-снапшоты и кэш сцены, ~0.8 с на 100 000 узлов) — периодически в простое и при закрытии.
- Журнал обновлений Loro (IndexedDB или файл рядом) пишется до основного файла; после сбоя изменения восстанавливаются при следующем открытии.
- В Tauri запись атомарная: временный файл → переименование.

## 11. Обработка ошибок

- Повреждённый файл: открывается всё, что прочитано, с понятным сообщением о потерянном (например, «Файл повреждён: не удалось прочитать секцию изображений. Документ открыт без 2 картинок»).
- Паника в Rust перехватывается (`console_error_panic_hook`), worker перезапускается, документ восстанавливается из журнала; интерфейс сообщает «Редактор перезапущен, изменения сохранены».
- Потеря GPU-устройства: пересоздание устройства и текстур, при неудаче — переход на запасной рендер.
- Ошибки пишутся в локальный лог; отправка отчётов — после появления сервера.

## 12. Тестирование

- `ferrum-doc`: тесты мутаций, undo/redo, стабильности `NodeId`, кэша сцены, чтения/записи `.ferrum` и повреждённых файлов; `proptest`: случайные последовательности операций не ломают дерево, зеркало свойств совпадает с честной перезагрузкой из Loro после каждой операции, undo и redo.
- Контрольный бенчмарк `bench_report` (цели из раздела 3) — обязательная проверка этапа 1 и регрессионная проверка в CI.
- `ferrum-editor`: сценарии без браузера (события ввода → проверка документа); тесты таблицы команд, раскладки и конфликтов.
- `ferrum-render`: эталонные изображения через `vello_cpu` с допуском.
- Бенчмарки `criterion` на 100 000 и 500 000 узлов с целями из раздела 3; запуск в CI для отлова регрессий.
- E2E: Playwright в Chrome и Firefox (нарисовать фрейм → сохранить → перезагрузить → открыть → сравнить).
