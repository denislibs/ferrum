# Ferrum — подсистема 1: ядро редактора

Дата: 2026-10-23 · Статус: на ревью

## 1. Контекст

Ferrum — векторный редактор для дизайна интерфейсов, аналог Figma. Ядро на Rust, интерфейс на SolidJS + TypeScript. Работает в браузере и как десктопное приложение (Tauri v2) из одной кодовой базы.

Проект разбит на подсистемы, у каждой свой цикл «спека → план → реализация»:

| № | Подсистема | Содержание |
|---|---|---|
| 1 | **Ядро редактора** (этот документ) | модель документа, рендер, холст, инструменты фигур, выделение, undo/redo, файлы, минимальный интерфейс |
| 2 | Оболочка редактора | контекстные меню, палитра команд, полировка панелей |
| 3 | Векторы и текст (спека `2026-10-29-ferrum-vectors-text-design.md`) | pen tool, векторные сети, булевы операции, текстовый движок, стрелка, Scale (K), экспорт SVG/PDF |
| 4 | Бэкенд и совместная работа | аккаунты, сервер, синхронизация Loro, курсоры, офлайн, серверное хранилище `.ferrum` |
| 5 | Дизайн-системы | auto layout, компоненты, варианты, переменные, стили, вкладка «Ассеты» |
| 6 | Прототипирование, плагины, Dev Mode | |
| 7 | Импорт из Figma (последней) | чтение `.fig` (формат Kiwi) как основной путь, Figma REST API как запасной; вставка из буфера обмена Figma |

Визуальный язык интерфейса задан дизайн-системой Ferrum: https://claude.ai/artifact/L9ZDGW6XCRGquBLYTtYYUK

Разработка: код пишет в основном Claude, автор проекта направляет и проверяет. Ключевые решения поясняются в коде и описаниях шагов.

## 2. Цели и не-цели

**В подсистеме 1 пользователь может:**
- создавать, открывать и сохранять файлы `.ferrum` (диск в Tauri; IndexedDB и File System Access в браузере);
- работать с несколькими страницами;
- рисовать фреймы (с пресетами размеров), прямоугольники, эллипсы, линии, группы, размещать изображения;
- выделять, перемещать, менять размер и поворачивать объекты, менять порядок и вложенность;
- измерять расстояния от выделения до объекта под курсором или до родительского фрейма, удерживая Alt (Option), как в Figma;
- задавать заливки (цвет, изображение), обводки, прозрачность, радиус скругления, обрезку содержимого фрейма;
- отменять и повторять действия;
- зумить от 2% до 25 600% и панорамировать бесконечный холст;
- экспортировать фрейм или выделение в PNG @1x/@2x/@3x;
- переназначать горячие клавиши.

**Не входит:** текст, pen tool, булевы операции, SVG/PDF-экспорт (подсистема 3); сервер и совместная работа (4); auto layout и компоненты (5); прототипы (6); импорт Figma (7); подсказки равных промежутков между соседями при перетаскивании, расстояния между несколькими наведёнными объектами и измерение в собственных осях повёрнутых объектов (позже).

## 3. Цели производительности

- Страница на 100 000 узлов открывается быстрее 2 с.
- Зум и панорамирование — 60+ fps на странице в 100 000 узлов.
- Перетаскивание 1000 выделенных объектов без просадки кадров.
- Интерфейс панелей не блокируется работой ядра.

Модель документа проверена бенчмарком до начала реализации (прототип, 2026-10-23). Наивная реализация на Loro не проходила цели: открытие 100 000 узлов — 4.6 с, файл — 44 МБ, undo — 818 мс, память при первом undo — ~550 МБ. Решения в разделе 5 (стабильные ID, значения вместо контейнеров, зеркало свойств, кэш сцены, shallow-снапшот, своя история отмены) приводят к целям этапа 1, которые контрольный бенчмарк `bench_report` проверяет на странице из 100 000 узлов (нативно, release; WASM ожидается в 1.5–2 раза медленнее):

| Метрика | Цель | Замер прототипа |
|---|---|---|
| Открытие до первого кадра (из кэша сцены) | ≤ 300 мс | 55 мс |
| Фоновая загрузка Loro | ≤ 1500 мс | 304 мс |
| Память открытого документа | ≤ 400 МБ | 149 МБ |
| Размер файла | ≤ 30 МБ | 26.6 МБ |
| Правка свойства | ≤ 1 мс | 0.01 мс |
| Undo одной правки / сдвига 1000 узлов | ≤ 50 мс | 0.0 / 1.3 мс |
| Сдвиг 1000 узлов одной транзакцией | ≤ 50 мс | 6.9 мс |
| Полное сохранение | ≤ 1500 мс | 780 мс |

Для 500 000 узлов (справочно): первый кадр — 0.38 с, фоновая загрузка — 2 с, память — 865 МБ, полное сохранение — 4.5 с. Полное сохранение такого размера блокирует worker, поэтому автосохранение пишет только инкрементальные обновления (раздел 10).

## 4. Архитектура

### 4.1 Репозиторий

```
ferrum/
├─ crates/                 Cargo workspace
│  ├─ ferrum-doc           модель документа на Loro: схема, мутации, undo/redo, формат .ferrum
│  ├─ ferrum-scene         производный кэш: мировые трансформы, bounds, R-tree (rstar), превью жеста
│  ├─ ferrum-render        vello_cpu / vello_gpu: сборка кадра, камера, оверлеи, кэши, экспорт PNG
│  ├─ ferrum-editor        инструменты, выделение, ввод, привязки, таблица команд, раскладка клавиш
│  └─ ferrum-wasm          wasm-bindgen: ядро worker'а, протокол обмена, поверхности рендера
└─ apps/
   ├─ web                  Vite + SolidJS + TypeScript
   └─ desktop              Tauri v2, оборачивает сборку apps/web
```

Границы крейтов:
- `ferrum-doc` не знает о рендере; остальные крейты не видят Loro напрямую, только API `ferrum-doc`.
- `ferrum-render` не знает о Loro и инструментах; получает сцену, камеру и описание оверлеев.
- `ferrum-editor` не зависит от браузера и тестируется обычным `cargo test`.

### 4.2 Потоки

```
Основной поток (Solid)                    Web Worker (Rust/WASM)
<canvas> → transferControlToOffscreen ──→ OffscreenCanvas + vello
ввод (SAB-буфер) ───────────────────────→ ferrum-editor → doc → scene → render
живое состояние (SAB) ←───────────────── X/Y/W/H выделения, камера, статистика кадра
команды (postMessage) ──────────────────→
события (postMessage) ←───────────────── выделение, структура слоёв, курсор, ошибки
буфер обмена, диалоги файлов ←─────────→ запросы/ответы, байты как transferable
```

Ядро с первого дня работает в выделенном Web Worker с OffscreenCanvas. Основной поток передаёт холст `transferControlToOffscreen`; worker (`WasmCore`) владеет редактором, документом, сценой и рендером. Интерфейс работает с ядром только через TypeScript-класс `Core` (`apps/web/src/core/core.ts`): `start`, `send(Command)`, `on(CoreEvent)`, `live` — живое состояние текущего кадра.

**Правило: основной поток тонкий.** Интерфейс только отображает готовые данные и пересылает ввод и команды; ничего, что зависит от размера документа, в основном потоке не вычисляется. Конкретно:
- Всё о документе — в воркере ядра: правки, undo/redo, hit-testing, привязки, инструменты, выделение, рендер, экспорт PNG, декодирование изображений.
- Панели получают из воркера готовые срезы: дерево слоёв — только видимые строки (виртуализация, поиск и фильтр по слоям, диапазон выделения с Shift считаются в воркере); свойства — только для выделения, уже сведённые (в том числе «Смешанные» для нескольких объектов); список страниц и файлов. Срезы уходят только при изменении (правка документа, выделение, страница, команда панели), не в каждом кадре.
- Палитра цвета, пипетка, превью картинок в панели — значения и уменьшенные копии готовит воркер; основной поток не держит пиксели документа.
- **Отдельный воркер ввода-вывода** для файлов: IndexedDB (записи, байты, превью, журнал изменений, настройки пользователя, дескрипторы файлов на диске) и чтение и запись файлов File System Access. Снимки и пачки журнала ядро отдаёт событиями, интерфейс передаёт их буферы worker'у ввода-вывода без копий. Исключение — десктоп: IPC Tauri есть только у окна, поэтому байты идут в Rust из основного потока тем же `ArrayBuffer` сырым телом запроса, а запись и `fsync` — в потоке Tauri.
- В основном потоке остаётся только то, что доступно лишь там: DOM интерфейса, события ввода, буфер обмена, диалоги файлов, CSS-курсор. Любая обработка этих данных (разбор вставленного содержимого, чтение файла, перекодирование картинок не в PNG) уходит в воркеры; размер картинки проверяется по заголовку до декодирования.
- Бюджет основного потока: любая задача ≤ 4 мс за кадр; длинные задачи (`longtask` > 50 мс) в основном потоке — регрессия, которую ловят E2E-тесты. Обработчик события ввода только кодирует запись (O(1)); `Core` сам меряет время обработчиков и кадра (`mainThreadStats`), в том числе кадр планировщика интерфейса и обработчики интерфейса, обёрнутые `costed` (прокрутка панелей, перетаскивание полей).

### 4.3 Протокол обмена

- Весь обмен идёт через интерфейс `Transport` (TypeScript). Реализация выбирается автоматически: SharedArrayBuffer + postMessage при `crossOriginIsolated`, иначе только postMessage.
- **SharedArrayBuffer** (65 856 байт, раскладка описана в `crates/ferrum-wasm/src/layout.rs`, TypeScript-константы генерируются в `apps/web/src/core/layout.gen.ts`, тест сверяет файл):
  - управление — 16 ячеек `Int32` под `Atomics`: счётчик кадров, позиции записи и чтения кольца, версия живого состояния, выброшенные события;
  - живое состояние — 32 ячейки `Float64`: кадры, время кадра (последнее, медиана, p95), fps, бэкенд, выделение (число и значения панели «Положение»), камера, холст, жест, история, узлы, записи ввода, атлас. Worker пишет его под seqlock (нечётная версия — идёт запись), основной поток читает в `requestAnimationFrame`;
  - кольцевой буфер ввода — 1024 записи по 64 байта: pointer (все `getCoalescedEvents()`), wheel, жесты щипка, key (`code` и `key` UTF-8 до 24 байт, AltGraph — только настоящее состояние), blur и размер холста с dpr (`ResizeObserver`). Один писатель и один читатель; счётчики монотонные, сравниваются по модулю 2³². Полное кольцо — записи ждут в очереди основного потока (до 4096) и уходят следующими кадрами в том же порядке.
- **postMessage** для команд и событий. Типы описаны в Rust (`protocol.rs`), TypeScript-типы (`Command`, `CoreEvent`, …) генерирует `tsify` при сборке wasm-bindgen (`Option` — `T | undefined`). Байты файлов, буфера обмена и пикселей — `Uint8Array`, буферы передаются transferable.
- **Команды и события панелей** (этап 5): окно строк дерева слоёв, раскрытие, поиск, выделение из панели (заменить, добавить, диапазон), наведение, имя, перенос и флаги слоёв; правка выделения из панели свойств с фазами превью / запись / отмена; страницы, фон страницы (превью — только в кадре), имя документа; пресет, зум, экспорт PNG, вставка картинки; раскладка (назначить, снять, сбросить, импорт) и настройки. События: окно слоёв, сводка выделения, страницы, раскладка с конфликтами и сочетаниями браузера, конфликт назначения, пресеты, экспорт, «документ изменён» (`modified`: любая правка с открытия, создания или сохранения в хранилище, и та, что не в истории, — страницы, фон, имя файла; по нему работает отложенное сохранение). Раскладка и пресеты уходят вместе с `ready`. Пределы: идентификаторы ≤ 64 байт, строки ≤ 4096 байт, списки ≤ 1000 идентификаторов, ≤ 64 заливок и обводок, окно слоёв ≤ 200 строк, JSON раскладки ≤ 64 КБ, картинки ≤ 64 МБ и ≤ 8192 px.
- **Снимок для хранилища** (этап 6): `Snapshot { thumbnail }` → событие `Snapshot { revision, name, bytes, thumbnail? }` — байты `.ferrum`, имя документа, ревизия правок и PNG превью первой страницы 480×320 (нет — страница пуста); `MarkSaved { revision }` после удачной записи снимает `modified`, только если ревизия та же (правка после снимка оставляет документ изменённым). `Save` → `Saved` — копия на диск, признак не снимает. Команда раскладки `file.save` (Ctrl/Cmd+S) даёт событие `SaveRequested`.
- **Журнал и восстановление** (этап 6): `FlushJournal` → всегда `Journal { batch, bytes?, failed }` (без байтов и без `failed` — правок с прошлой пачки нет; `failed` — пачку собрать не удалось, рядом идёт `Error`, начало журнала не сдвинуто и те же правки уйдут следующей удачной пачкой); пачка уходит и перед каждым `Snapshot`, поле которого `journal` — номер последней вошедшей пачки. `OpenWithJournal { bytes, journal }` применяет пачки поверх файла; применено хоть что-то — `Recovered { batches }` перед `Opened`, документ изменён. Пачек ≤ 100 000, файл вместе с журналом ≤ 512 МБ (проверяют обе стороны). Потеря GPU: `SurfaceLost { backend }` (worker создаёт поверхность заново: `WasmSurface.create` → `replaceSurface`), `SurfaceRestored`, `SurfaceFailed { next }` (интерфейс перезапускает ядро с бэкендом `next`). Тестовая паника `testPanic` принимается только в тестовом режиме (`init.test`).
- **Адресат правки из панели** — те, кого выделяли в начале жеста (набора в поле, жеста палитры, перетаскивания строк слоёв), а не выделение на момент записи. Если выделение не больше предела идентификаторов (1000), команда несёт их `ids`; если больше — без `ids`, с `selectionVersion` из события `selection` на начало жеста, и ядро применяет её ко всему выделению, только пока версия та же; иначе — одна ошибка «Выделение изменилось — правка не применена», без шага и без превью. Так устроены `EditSelection` и `MoveLayers` (невыделенная строка слоя переносится одна — по своему id).
- **Конверты, кроме команд и кадра:** `pasteText` — текст с меткой `ferrum-clipboard:v1:` из буфера обмена; основной поток только переносит его, base64 декодирует worker и выполняет `paste`. `encodeClipboard` — байты для запасного пути записи в буфер (браузер отказал асинхронному API); worker отвечает `clipboardText` с текстом с меткой или `null` при отказе (ошибка — событием). Размер и вид обоих проверяют обе стороны (текст и байты — ≤ 64 МБ).
- **Запасной режим без изоляции:** те же записи ввода копятся в буфере и уходят сообщением кадра; живое состояние приходит ответным сообщением; следующий кадр не отправляется, пока не пришёл ответ (медленный worker не копит очередь).
- Всё, что пересекает границу, не доверенное: непонятная запись пропускается и считается, счётчик записи из общей памяти не читается дальше ёмкости кольца, неверная команда — событие `error`, а не паника worker'а.
- Требуются заголовки `Cross-Origin-Opener-Policy: same-origin` и `Cross-Origin-Embedder-Policy: credentialless` в Vite (`server` и `preview`), на хостинге и в Tauri. Следствие для подсистемы 4: вход через OAuth делается редиректом, не попапом.
- Многопоточный WASM (`wasm-bindgen-rayon`, nightly Rust) заложен как возможность и включается по результатам бенчмарка. Сборка — `wasm32-unknown-unknown` с SIMD128.

### 4.4 Планировщик интерфейса

Собственная реализация идей fasterdom (код Telegram Web A не используется: он под GPL-3.0), `apps/web/src/ui/scheduler.ts`:
- кадр планировщика вызывает `Core` из своего `requestAnimationFrame` (`onFrame`), после тика транспорта и чтения живого состояния, — время планировщика и обновлений Solid входит в бюджет основного потока;
- сначала фаза `measure`: чтения layout и живого состояния из общей памяти (подписчики `everyFrame` возвращают запись для следующей фазы); затем фаза `mutate` — одна `batch()` Solid: события из worker'а, пришедшие с прошлого кадра, записи подписчиков, ручные записи в DOM. Так чтения не заставляют браузер пересчитывать раскладку после записей того же кадра;
- живые значения жеста (X/Y/W/H/поворот одного узла, зум) панель берёт из живого состояния в фазе `measure`, а не из событий;
- ошибки ядра применяются сразу, мимо очереди: после остановки ядра кадров нет, и сообщение иначе не дошло бы;
- в dev-режиме предупреждение (одно на имя) при чтении layout вне фазы `measure`.

## 5. Модель документа (`ferrum-doc`)

### 5.1 Структура

- **Корневой LoroDoc:** `meta` (`schemaVersion`, имя файла), упорядоченный список страниц (id, имя, цвет фона `#rrggbbaa` — не записан, если как у холста в теме). Операции со страницами и фон в историю отмены не попадают; последнюю страницу удалить нельзя. В подсистеме 5 здесь появятся компоненты.
- **Один LoroDoc на страницу:** `LoroTree` узлов страницы. Загружается только открытая страница, остальные — по требованию.
- Перенос узлов между страницами выполняется как копирование + удаление; отменяется двумя шагами.

### 5.2 Узлы

- **Стабильный ID узла** (`NodeId`) — `TreeID` его первого создания, записанный ключом `id` в свойства узла. Loro при восстановлении удалённого узла выдаёт ему новый `TreeID`, но копирует свойства, поэтому `NodeId` переживает undo/redo и перезагрузку. Страница держит индекс «`NodeId` → текущий `TreeID`». Порядок детей — дробные индексы Loro.
- Типы: `frame`, `group`, `rect`, `ellipse`, `line`, `image`. Новые типы добавляются без миграции старых файлов.
- Каждое свойство — отдельный ключ в `LoroMap` узла: `id, type, name, x, y, w, h, rotation, opacity, visible, locked, cornerRadius, clipContent, flipX, flipY, fills, strokes`.
- **Нейтральные значения не записываются:** `x`, `y`, `rotation`, `cornerRadius` = 0, `opacity` = 1, `visible` = true, `locked`, `flipX`, `flipY` = false подставляются при чтении. Поэтому нейтральные значения по умолчанию в схеме менять нельзя.
- Координаты `f64` в пикселях, относительно родителя. Линия: длина `w`, `h = 0`, поворот.
- **Отражение** `flipX`/`flipY` — по осям узла, относительно центра его рамки, до поворота: локальная матрица `T(x, y) · R(rotation) · F`, `F = translate(w/2, h/2) · scale(±1, ±1) · translate(−w/2, −h/2)`. Рамка переходит сама в себя, поэтому `x`, `y`, `w`, `h` и границы от отражения не зависят; отражается содержимое — заливка изображением и дети фрейма или группы (как в Figma). У группы рамки нет (`w = h = 0`), её `F` — относительно начала координат группы; редактор группы не отражает, а переписывает их детей. Группа хранит `x`, `y`, `rotation`, но не `w`/`h`: её границы вычисляются по детям. Перемещение группы меняет только её `x`/`y`; ресайз группы масштабирует геометрию детей в одной транзакции.
- `fills`: неизменяемое значение-список (не контейнер Loro) из `{ kind: solid | image, color: "#rrggbbaa", imageHash, scaleMode: fill | fit | tile, opacity, visible }`, снизу вверх; заменяется целиком. Контейнер на каждую заливку раздувал файл почти втрое.
- `strokes`: такое же значение-список из `{ color, width, align: inside | center | outside }`.

### 5.3 Зеркало свойств и кэш сцены

- Чтение свойства из Loro стоит ~9 мкс на узел. Страница держит **зеркало свойств** всех живых узлов в памяти: наши правки обновляют его напрямую, загрузка без кэша заполняет его один раз из Loro. `props()`, кэш сцены и ссылки на изображения читаются из зеркала.
- **Кэш сцены** — плоская таблица всех узлов страницы (стабильный ID, текущий `TreeID`, индекс родителя, все свойства) в порядке обхода. Пишется в файл при каждом сохранении вместе с хэшем снапшота, из которого построен.
- **Открытие файла:** таблица читается сразу (55 мс на 100 000 узлов), и холст рисуется по ней. Loro раскодируется в фоне внутри worker'а; индекс и зеркало берутся из таблицы без чтения Loro. До окончания фоновой загрузки правки недоступны. Если хэш не совпал или таблица повреждена, кэш молча игнорируется и страница загружается из Loro.
- Подсистема 4 (импорт чужих правок) добавит обновление зеркала и индекса по событиям Loro для изменённых узлов.

### 5.4 Изображения и формат `.ferrum`

- Байты изображений не хранятся в Loro; узел ссылается на хэш blake3.
- Контейнер `.ferrum`: `magic "FERRUM\0\0" · версия формата · секции`. Секция: `тип · id · длина · blake3(данных) · данные`. Типы: корневой документ, shallow-снапшот страницы, ссылки страницы на изображения, изображение по хэшу, кэш сцены страницы. Повреждённая секция пропускается с предупреждением; неизвестные типы секций (из будущих версий) пропускаются.
- Страницы сохраняются **shallow-снапшотом** Loro — текущее состояние без истории правок: он на треть меньше полного, быстрее раскодируется и для документа после правок быстрее экспортируется. История между сессиями не нужна: отмена работает в пределах сессии, версии файла появятся с сервером.
- Неиспользуемые изображения не записываются.
- `meta.schemaVersion` + цепочка миграций при открытии старых файлов. Файл более новой версии открывается только для чтения с предупреждением.
- Loro зафиксирован на 1.16.2 вместе с `loro-internal` 1.16.2: с `loro-internal` 1.17 эта версия не собирается.

### 5.5 Транзакции и история

- API: `create_node`, `set_props(id, patch)`, `move_node(id, parent, index)`, `move_nodes(ids, parent, index)`, `delete_nodes`, `Document::transact(page, selection, |page| …)`. Позиция за концом списка детей, вплоть до `usize::MAX`, означает «в конец».
- **Уведомления об изменениях.** Транзакции, undo и redo копят по странице `Changes { created, deleted, moved, props }` — стабильные `NodeId`, выведенные из журнала обратных операций; `Document::take_changes(page)` забирает их раз за кадр. При ошибке транзакции туда попадают затронутые узлы: сцена сверяет каждый узел с текущим состоянием страницы, поэтому лишние записи безвредны. `PageDoc::placement(id)` отдаёт родителя и позицию узла за O(log n).
- **Своя история отмены, без `UndoManager` Loro.** Первый undo через `UndoManager` на 100 000 узлах стоил 0.35–0.75 с и ~450 МБ памяти (Loro строит внутренние структуры на весь документ). Вместо этого каждая правка записывает в журнал транзакции обратную операцию: для изменения свойств — прежние значения изменённых полей (из зеркала), для создания — удаление, для удаления — восстановление поддерева с прежними `NodeId`, для перемещения — возврат на прежнее место. Undo применяет обратные операции и записывает их собственные обратные для redo. Память растёт с числом правок, а не с размером документа. Отмена создаёт новые операции Loro и отменяет только свои правки — так же, как `UndoManager`.
- Глобальный стек хранит шаги всех страниц в порядке действий пользователя. Одно действие (например, от нажатия до отпускания мыши) — один шаг; транзакция без изменений шага не создаёт — правка свойств теми же значениями не пишется и обратной операции не записывает. При ошибке внутри транзакции её изменения откатываются обратными операциями.
- Выделение не хранится в документе, но сохраняется в шаге и восстанавливается при undo/redo.
- Во время перетаскивания, ресайза и поворота изменения живут только как временное превью в `ferrum-scene`; в Loro записывается одна транзакция при отпускании. В подсистеме 4 живое превью для других участников пойдёт через `EphemeralStore`.

## 6. Сцена (`ferrum-scene`)

- Производный кэш из документа: локальная и мировая матрицы (`kurbo::Affine`, f64; поворот вокруг левого верхнего угла, как в Figma, и отражение относительно центра рамки, раздел 5.2), границы формы в локальных координатах (у группы — объединение видимых детей), границы узла с обводкой в мире, границы видимого поддерева (фрейм с обрезкой не выходит за себя) и R-tree (`rstar`) по мировым границам узлов для hit-testing и запросов по рамке.
- При открытии файла строится из кэша сцены (раздел 5.3), до загрузки Loro; строки не доверенные — значения проверяются, повторы `NodeId` отбрасываются вместе с поддеревом. Дальше обновляется по `Changes` (раздел 5.5): пересчитываются только затронутые узлы, мировые матрицы их потомков и границы предков; новые узлы встают на место по `placement` без перечитывания списков соседей.
- Узел хранит две версии: `version` растёт при изменении вида в локальных координатах (тип, размер, скругление, заливки, обводки) — по ней устаревает список отрисовки; `subtree_version` — при любом изменении поддерева — по ней устаревает растровый кэш фрейма.
- Hit-test: R-tree отбирает кандидатов, затем точная проверка формы с поворотом и обводкой, видимости узла и предков и обрезки фреймами-предками; результат — все узлы под точкой, верхний первым (правила выделения — в редакторе).
- Слой временного превью поверх документа для текущего жеста: временные правки свойств узлов, документ не меняется.
- Черновики жеста — временные узлы, которых нет в документе: рисуемая фигура и копии при перетаскивании с Alt. Идентификатор черновика — `NodeId` с пиром `u64::MAX`, который Loro узлам не выдаёт. Черновик встаёт верхним ребёнком своего родителя (узла документа или другого черновика), двигается тем же превью и уходит вместе с ним (`clear_preview`); `apply` на время обновления убирает черновики и ставит обратно, потому что позиции в `Changes` посчитаны без них.
- `rstar` зафиксирован на 0.12.2: в 0.13.0 вставка после пакетного построения падает (листья на разной глубине).

## 7. Редактор (`ferrum-editor`)

Редактор не зависит от браузера и ОС и детерминирован: ввод приходит простыми структурами (указатель с точкой в CSS-пикселях, кнопкой, модификаторами и временем события; колесо; щипок; клавиша с физическим `code`, символом `key` и модификаторами; потеря указателя и фокуса), время двойного клика берётся из событий. Одна последовательность событий всегда даёт один документ. `Editor` владеет документом, сценой, камерой, выделением, инструментом и раскладкой клавиш: сцена должна совпадать с документом после каждой правки, и это гарантируется тем, что править документ больше некому — панели правят через `Editor::transact`. Рендер получает `scene()`, `camera()` и `overlay()` по ссылке.

### 7.1 Инструменты

Трейт `Tool`: `pointer_down / move / up`, `key` (модификаторы изменились во время жеста), `cancel`, `is_busy`, `cursor()`, `overlay()`. На событие инструмент получает контекст: документ, сцену, камеру, выделение, наведение, настройки.

| Инструмент | Клавиша | Назначение |
|---|---|---|
| Перемещение | V | выделение, перемещение, ресайз, поворот |
| Фрейм | F, A | рисование фрейма; пресеты размеров |
| Прямоугольник / Эллипс / Линия | R / O / L | рисование фигур |
| Рука | H, удержание Space, средняя кнопка | панорамирование |
| Изображение | Ctrl/Cmd+Shift+K, вставка, перетаскивание файла | размещение изображения |

Правило всех жестов: пока кнопка нажата, изменения живут только в превью сцены и черновиках; при отпускании записывается одна транзакция — один шаг отмены; Esc, потеря указателя и потеря фокуса окна отменяют жест без следа в истории. Во время жеста клавиши только меняют модификаторы, Esc отменяет жест (физическая клавиша Escape, как бы ни была переназначена команда «Отмена»); второе нажатие без отпускания отменяет прежний жест.

Инструмент «Перемещение»: состояния `Idle → Pressed → Dragging | Marquee | Resizing(handle) | Rotating | LineEnd`; перетаскивание начинается после 3 экранных пикселей. При нажатии по порядку проверяются: ручки (8 px, ловятся в радиусе 6 px; углы раньше середин сторон; сторона рамки — по всей длине в 4 px), зона поворота (снаружи угловой ручки, до 16 px от угла), название фрейма, узел по правилам выделения, пустое место внутри общей рамки нескольких выделенных (тащит их все), пустой холст (рамка выделения). У выделенной линии вместо рамки — ручки на концах.

Рисование: пока кнопка нажата, фигура — черновик сцены, выделенный в оверлее; клик без перетаскивания создаёт фигуру 100 × 100 (линию длиной 100, изображение — в исходном размере); так же создаётся фигура, которую дотянули меньше чем на 1 px по любой оси (линия — короче 1 px), например обратно к точке начала. Фигура встаёт в самый глубокий фрейм под точкой нажатия. После рисования она выделена, а редактор возвращается к «Перемещению», как в Figma. Изображение размещается по хэшу и размеру, которые даёт интерфейс (байты кладутся в документ через редактор); перетаскивание сохраняет пропорции.

Камера (раздел 8.3): колесо с Ctrl/Cmd и щипок зумят к курсору с множителем `exp(−deltaY · 0.01)`, без модификатора колесо панорамирует, с Shift — вбок; если идёт жест, он пересчитывается под новой камерой.

### 7.2 Выделение

- Клик выбирает объект верхнего уровня; внутри фрейма верхнего уровня (он ведёт себя как монтажная область) — его ребёнка верхнего уровня. Пустое место фрейма верхнего уровня с детьми не выбирает фрейм — с него начинается рамка; фрейм выбирается кликом по названию над ним. Фрейм без детей выбирается кликом внутри.
- Если выделение уже внутри контейнера, клик по соседям выделенных выбирает их на том же уровне. Двойной клик (не дольше 500 мс и 4 px) — на уровень глубже; Ctrl/Cmd+клик — самый глубокий объект под курсором.
- Shift+клик добавляет объект при нажатии и убирает выделенный при отпускании без перетаскивания; клик по одному из нескольких выделенных при отпускании оставляет только его.
- Рамка выделения работает в контексте точки начала: начатая во фрейме верхнего уровня выбирает его детей, на холсте — объекты верхнего уровня, причём фреймы верхнего уровня — только охваченные целиком. Пересечение — по рамкам в мире; скрытые и заблокированные не выбираются; с Shift рамка добавляет к выделению, Esc возвращает выделение до рамки. Кандидаты — дети контекста перебором, если их не больше 4096, иначе запрос к R-tree.
- Перетаскивание: если отпустить над другим фреймом (самым глубоким под курсором, не из перетаскиваемых), чем родитель узла, за который взялись, узлы, чей родитель — фрейм или корень, становятся детьми этого фрейма; вынесенные за фрейм на холст — уходят в корень. Положение и поворот на экране сохраняются. Из групп узлы при перетаскивании не выходят (группа растёт вместе с ними). Превью меняет только свойства, поэтому новый родитель применяется при отпускании.
- Заблокированные и скрытые узлы на холсте не выбираются и не подсвечиваются, клик проходит сквозь них; заблокированные выделенные (из панели слоёв) не двигаются жестами и стрелками.

### 7.3 Модификаторы и привязки

- Shift: пропорции при ресайзе и рисовании, квадрат и круг, линия с шагом 45°, движение по оси, поворот шагом 15° (угол единственного узла кратен 15°, у нескольких — общий поворот). Alt: ресайз и рисование от центра; Alt+перетаскивание — копия: двигаются черновики-копии, Alt включает и выключает копию прямо во время жеста; при отпускании копии создаются одной транзакцией прямо над оригиналами и выделяются.
- Ресайз: 8 ручек; одного узла — в его собственных осях (поворот сохраняется), нескольких — общей рамкой в мире. Ресайз группы масштабирует детей в координатах группы (раздел 5.2), дети фреймов не масштабируются. Ресайз за противоположную сторону отражает фигуру, как в Figma: ручка остаётся под курсором, рамка — положительной (`w`, `h` ≥ 0; сторона узла после ресайза не меньше 0.01, как в Figma, иначе схлопнутую сторону нельзя было бы растянуть обратно), а у одного узла переключается отражение той оси узла, сторону которой перешли (угол за обе стороны — обе оси, без поворота на 180°); обратный переход снимает его. У нескольких узлов и у детей группы отражается рамка жеста (мир или группа), и правило одно для любого угла: отражение по оси x рамки переключает `flipX` каждого узла, по оси y — `flipY`, а поворот θ относительно рамки становится −θ; новая матрица узла раскладывается с учётом знака определителя, и повтор отражения возвращает узел как был. Shift и Alt работают и при отражении, привязки — и у отражённых узлов. «Отразить по горизонтали / по вертикали» (Shift+H, Shift+V) отражают выделение относительно центра его рамки по оси мира одним шагом отмены. Поворот — вокруг центра рамки; модель хранит поворот вокруг левого верхнего угла, поэтому `x`/`y` пересчитываются.
- Свойства после жеста получаются разложением новой локальной матрицы узла на положение, поворот, размер и отражение; для сдвига, поворота и ресайза в осях узла это точно, у повёрнутого узла в общей рамке скос теряется (как в Figma).
- Привязка к краям и центрам соседей (детей родителей двигающихся узлов) и рамок родительских фреймов, порог 4 экранных пикселя, красные линии-подсказки от двигающейся рамки до совпавших соседей. При перетаскивании привязываются края и центр рамки, при ресайзе — точка ручки (у неповёрнутой рамки), при рисовании — текущая точка. Кандидаты ищутся двумя запросами к R-tree по полосам вокруг двигающихся координат в видимой части холста: такая полоса содержит все узлы с краем или центром ближе порога, поэтому находятся ровно все привязки в видимой части, а работа не зависит от размера страницы.
- Измерение с Alt (Option на macOS; та же физическая клавиша `AltLeft`/`AltRight` везде), как в Figma: пока Alt нажат, выделение не пустое, инструмент — «Перемещение», нет жеста холста или панели (перетаскивание подписи поля, палитра) и курсор не над ручками рамки, оверлей показывает расстояния от рамки выделения S. Рамки — в мире (у повёрнутых тоже, как в Figma), без обводок, как у бейджа размера. До наведённого объекта T: если рамки пересекаются (T охватывает S, S охватывает T или частичное перекрытие) — расстояния между одноимёнными краями слева, справа, сверху и снизу, линия — посередине общей части рамок по другой оси (у вложенных — по центру внутренней); если не пересекаются — по каждой оси с зазором расстояние между ближайшими краями, линия посередине перекрытия по другой оси, а без перекрытия — от центра S с пунктирной направляющей вдоль измеренного края T до самого T, если линия проходит мимо этого края (у S нулевой высоты или ширины на уровне края T её нет; по диагонали — обе оси). Без наведённого объекта или над родительским фреймом — четыре расстояния до внутренних краёв ближайшего фрейма-предка общего родителя выделенных (группы пропускаются); в корне — ничего. Над выделенным объектом — ничего. Отрезки идут от края S к краю T; значения — в единицах документа, до сотых без нулей в конце, как в панели свойств; нулевые не рисуются. Обводка наведения остаётся как обычно. Измерения обновляются при движении указателя, нажатии и отпускании Alt, смене выделения, правке и камере (колесо, щипок и смена камеры без жеста повторяют hit-test наведения под указателем, поэтому и цель, и обводка наведения следуют за камерой); отпускание Alt и потеря фокуса окна их убирают. Во время жестов (перетаскивание, ресайз, поворот, рисование, рамка выделения) их нет, и Alt сохраняет прежние значения: копия, от центра. Признак Alt ведётся и по клавишам, и по модификаторам указателя (потерянное нажатие или отпускание исправляет первое движение); на Windows и Linux AltGr (`alt_graph`; указатель видит его как Ctrl+Alt, поэтому признак запоминается по последней клавише) измерений не включает. Рамка, множество и родительский фрейм выделения кэшируются по версии выделения и счётчику сцены — на движение O(1) плюс hit-test наведения. Интерфейс отменяет отпускание одиночного Alt (без других клавиш после нажатия), когда клавиши у холста (фокус на холсте или ни на чём — клавиши и тогда идут холсту): на Windows оно уводило бы фокус в меню браузера; в полях ввода и в сочетаниях Alt остаётся браузеру.
- Привязка к целым пикселям включена по умолчанию, отключается в настройках: положение (у неповёрнутых узлов) и размеры округляются до целых; привязка к соседу важнее.

### 7.4 Hit-testing

R-tree отбирает кандидатов по bounds, затем точная проверка геометрии kurbo с учётом поворота и толщины обводки. Допуск для тонких линий — 4 экранных пикселя (делённые на зум). Подсветка наведения подчиняется тем же правилам выделения, что и клик; скрытые узлы не подсвечиваются.

### 7.5 Пресеты фреймов

Отдельный JSON-файл в крейте (`assets/frame_presets.json`, с разделами «Телефоны», «Планшеты», «Десктоп», «Соцсети», «Бумага»), по умолчанию: iPhone 16 (393×852), iPhone 16 Pro Max (440×956), Android Compact (412×917), iPad mini (744×1133), iPad Pro 11" (834×1194), Desktop (1440×1024), MacBook Air (1280×832), 1920×1080, Instagram post (1080×1350), Story (1080×1920), A4 (595×842). Список дополняется без изменения кода; размеры проверяются при разборе. Фрейм из пресета встаёт справа от содержимого страницы с зазором 100 px и выделяется; если его не видно, камера переезжает к нему.

### 7.6 Команды и горячие клавиши

- Единая таблица команд в Rust (43 команды: стабильный ключ вида `edit.duplicate`, русское название, сочетания); меню интерфейса вызывают команды по ID.
- Раскладка по умолчанию повторяет Figma, с вариантами Cmd (macOS) и Ctrl (Windows/Linux): V, F/A, R, O, L, H, удержание Space, Ctrl+Shift+K; Delete и Backspace; Ctrl+D; Ctrl+G / Ctrl+Shift+G; Ctrl+Alt+G; Ctrl+] / Ctrl+[ (на передний/задний план — с Alt на macOS, ⌥⌘] / ⌥⌘[, и с Shift на Windows и Linux, Ctrl+Shift+] / Ctrl+Shift+[, как в Figma для Windows: там Ctrl+Alt — это AltGr); стрелки 1px, Shift+стрелки 10px; Shift+1 (показать всё), Shift+2 (к выделению), Shift+0 (100%), = и − (приблизить и отдалить; ещё Shift+= и + / − цифрового блока); Ctrl+Shift+H (скрыть/показать); Ctrl+Shift+L (заблокировать); Shift+H и Shift+V (отразить по горизонтали и по вертикали); Ctrl+\ (скрыть интерфейс); Ctrl+C / Ctrl+V / Ctrl+X; Ctrl+Shift+C (копировать как PNG); Ctrl+A; Esc; Ctrl+Z / Ctrl+Shift+Z, на Windows и Linux ещё Ctrl+Y.
- **Переназначение:** экран настроек с поиском; хранятся только отличия от раскладки по умолчанию — полный новый список сочетаний у изменённых команд (JSON `{"format": "ferrum-keymap", "version": 1, "overrides": {"tool.rect": ["KeyQ"]}}`); список, совпавший с умолчанием, перестаёт быть отличием. Обнаружение конфликтов: `bind` без замены возвращает занятые команды, с заменой снимает с них сочетание; `conflicts()` показывает все сочетания с несколькими командами. Сброс одной команды или всех; импорт и экспорт JSON. Импорт не доверенный: ошибка формата не меняет раскладку, неизвестные команды и непонятные сочетания пропускаются с предупреждениями, размер ограничен 64 КБ.
- Сочетания сопоставляются по `KeyboardEvent.code` и точному набору модификаторов, поэтому работают на любой раскладке (включая русскую); знаки — по физической клавише раскладки US, как в Figma. На Windows и Linux с AltGr (`KeyEvent.alt_graph` — только по настоящему состоянию AltGraph; приходит он как Ctrl+Alt) сочетания с Mod+Alt не срабатывают: пользователь набирает символ. На macOS флаг не учитывается: AltGr там нет, а Option некоторые браузеры отдают как AltGraph. Подписи показываются для текущей раскладки через `navigator.keyboard.getLayoutMap()`, где доступно; без неё — подписи US (`⇧⌘K`, `Ctrl+Shift+K`).
- В веб-версии сочетания, которые перехватывает браузер (Ctrl/Cmd+W, T, N, с Shift, Tab, PageUp/PageDown; на macOS ещё Cmd+Q, H, M и Ctrl+Tab, Ctrl+Shift+Tab; на остальных Alt+F4, F11), помечаются предупреждением — список отдаёт `browser_reserved`; в Tauri доступны все.
- Если фокус в поле ввода панели, клавиши обрабатывает интерфейс.
- Настройки хранятся у пользователя, не в документе: в браузере — IndexedDB (хранилище `settings`, по ключу на поле: тема, привязка к пикселям, отличия раскладки, ширина панелей, раскрытие страниц, вид экрана файлов), в Tauri — файл конфигурации `settings.json`. Вкладка пишет только изменённые относительно того, что прочитала или записала сама, поля; другие вкладки получают их через `BroadcastChannel('ferrum-settings')` и применяют тему, привязку, раскладку клавиш и вид экрана файлов на лету — вкладки не затирают чужие поля. Ширины панелей и раскрытие страниц у каждой вкладки свои: чужие значения база запоминает, а вкладка их не применяет. Значения не доверенные: неверное поле — умолчание, поле больше 80 КБ отвергается. Чтение при запуске ждёт не дольше 2,5 с (база не отвечает — умолчания и одно уведомление). Запись идёт через worker, который уничтожается вместе со страницей раньше, чем запись дойдёт до базы, поэтому каждое изменение сначала синхронно ложится в запасную запись `localStorage` (`ferrum.settings.pending`, ≤ 80 КБ), убирается из неё после удачной записи, а при запуске оставшиеся поля применяются поверх базы и дописываются в неё. При первом запуске этапа 6 прежняя запись `localStorage` (`ferrum.settings.v1`) переносится и удаляется; тему до первого рисования `theme-init.js` берёт из зеркала `localStorage` `ferrum.theme`. Файл раскладки несёт платформу (`"platform": "mac" | "windows" | "linux"`): импорт с другой группы платформ меняет Ctrl и Cmd местами с одним предупреждением.
- Экран настроек: таблица команд по группам с поиском; новое сочетание записывается с клавиатуры по `code`; занятое — предложение заменить; конфликты и сочетания браузера помечены словом и иконкой; сброс одной и всех; импорт и экспорт JSON. Подсказки и пункты меню показывают сочетание из действующей раскладки.

### 7.7 Буфер обмена

- Ctrl+C кладёт формат `web application/x-ferrum` (в браузере — через асинхронный Clipboard API, где он умеет свои форматы, `ClipboardItem.supports`; иначе текстом base64 за меткой `ferrum-clipboard:v1:` в `clipboardData` события `copy`, которое вызывает `execCommand('copy')`): `FERRUMCB` · версия · JSON узлов (порядок обхода, родитель — индекс раньше в списке; у корней мировое положение, поворот и отражение; поля отражения необязательные и пишутся только со значением `true`, поэтому версия формата не менялась) · байты изображений, на которые ссылаются заливки. Копия самодостаточна и вставляется в другой документ. Ctrl+X — копия и удаление.
- Вставка не доверяет данным: размер, число узлов, изображений и заливок ограничены, ссылки на родителя — только назад, цвета, режимы и хэши проверяются, числа приводятся к пределам сцены, неизвестные типы узлов пропускаются с поддеревом; при ошибке документ и история не меняются. Узлы получают новые идентификаторы и выделяются. Цель — единственный выделенный фрейм, иначе родитель выделения, иначе корень; место — исходное, если оно видно и помещается в цель, иначе центр цели.
- Ctrl+Shift+C — копирование как PNG: редактор сообщает узлы, экспорт и запись в системный буфер делает worker и интерфейс.
- Вставка изображений из системного буфера (PNG, JPEG, WebP; не PNG перекодирует worker) — в центр видимой части или выделенного фрейма в исходном размере. Пока картинка перекодируется, следующие команды ждут — порядок команд не меняется.
- В браузере Ctrl/Cmd+C, X, V, пока раскладка связывает их с копированием, вырезанием и вставкой, идут событиями `copy`, `cut`, `paste` документа, а не клавишами в ядро; в полях ввода, диалогах (и немодальной палитре цвета) и меню это обычный текст.

### 7.8 Путь события

SAB-буфер ввода → worker в начале кадра передаёт события по порядку в `Editor::handle` → инструмент обновляет превью и черновики сцены → при отпускании изменения записываются в Loro одной транзакцией (один шаг undo) → редактор забирает `take_changes` всех страниц и применяет изменения текущей к сцене (то же после undo и redo; отмена шага другой страницы переключает на неё). Интерфейс получает события только при изменении: выделение, инструмент, курсор, «нужен кадр» (сцена, камера, оверлей), документ изменён, страница, байты для буфера обмена, запросы (прочитать буфер, выбрать изображение, экспорт PNG, скрыть интерфейс), ошибки.

## 8. Рендер (`ferrum-render`)

### 8.1 Бэкенд

Семейство vello на разреженных полосах (sparse strips): `vello_gpu` (бывший `vello_hybrid`) с бэкендом wgpu (WebGPU) в OffscreenCanvas, запасные варианты — `vello_gpu` с бэкендом `webgl` (WebGL2), затем `vello_cpu` с выводом `putImageData`. Классический `vello` (compute) не используется. Десктоп в первой версии использует тот же путь, что и браузер.

Выбор — при старте, по порядку, первый подошедший; причины отказов уходят в событии `ready`, активный бэкенд показан в живом состоянии. Контекст холста выбирается один раз, поэтому каждый вариант сначала проверяется без холста: адаптер и устройство WebGPU, пробный OffscreenCanvas 1×1 для WebGL2. Программный GPU (SwiftShader, запасной адаптер WebGPU) при автовыборе пропускается — он медленнее `vello_cpu` и тормозит выдачу кадров; явно запрошенный бэкенд берётся и программным. `WebGlRenderer` vello принимает OffscreenCanvas как `HtmlCanvasElement` (вызов `getContext` идёт по имени метода). WebGPU запрашивает пределы адаптера, а не умолчания (холст шире 8192 пикселей устройства).

Рендер рисует через свой трейт `RenderBackend` — общее подмножество API `vello_cpu::RenderContext` и `vello_gpu::Scene`: матрица, краска (цвет или изображение), заливка пути и прямоугольника, обводка (для оверлеев), обрезка путём, слой прозрачности. Сборка кадра одна для всех бэкендов. Эталонные тесты и экспорт PNG — через `vello_cpu`; E2E-тест читает пиксели каждого бэкенда и сверяет с тем же кадром `vello_cpu` (средняя разница < 0.1 по каналу).

Изображения в `vello_gpu` живут в атласе рендерера (страницы до 4096², не больше четырёх). `GpuBackend` грузит картинку при первом использовании по ключу — blake3 картинки документа или номеру построения растра фрейма — и вытесняет давно не рисовавшиеся, но никогда не нарисованные в текущем кадре. Место выделяется зеркальным кэшем `vello_common::image_cache` с той же конфигурацией: wgpu-рендерер vello при нехватке места паникует, а зеркало знает заранее; номер устройства сверяется с зеркальным. Очистка освобождённого места у WebGPU отправляется сразу: загрузка идёт `queue.write_texture`, которая выполняется раньше команд следующего `submit`. Картинка больше страницы уменьшается один раз при загрузке. Растровый кэш фреймов работает и на GPU.

Предел времени на растры за кадр считается по часам трейта `Clock`: нативно `Instant`, в worker'е `performance.now()` (`Instant` в wasm32 паникует).

### 8.2 Цикл кадров

Основной поток в `requestAnimationFrame` увеличивает счётчик кадров в SAB и вызывает `Atomics.notify`; worker ждёт в `Atomics.waitAsync`. Если счётчик уже ушёл вперёд (прошлый кадр был долгим), ожидание возвращается сразу, и worker явно уступает циклу событий, чтобы дошли команды. В начале кадра worker забирает все записи кольца и отдаёт их редактору по порядку, затем рисует, пишет живое состояние и отправляет события. Без изоляции кадр — сообщение основного потока с записями ввода; worker без `Atomics.waitAsync` будится таким же сообщением. Кадр рисуется только при изменении сцены, камеры или оверлея (`NeedsRedraw`) или если прошлый кадр неполный (`needs_another_frame`: растры не догнали, картинки декодируются).

### 8.3 Камера и точность

- Центр в `f64`, зум 0.02–256, зум колесом к курсору, щипок тачпада (Ctrl+wheel).
- Матрица «мир → пиксели устройства» собирается в `f64` относительно центра камеры; vello применяет её к путям в `f64` и переводит в `f32` уже экранные координаты — без дрожания на больших координатах (узел на 1e7 рисуется пиксель в пиксель как у начала координат).
- `devicePixelRatio` учитывается; размер канваса отслеживает `ResizeObserver` в основном потоке и передаёт через SAB.

### 8.4 Сборка кадра

Бэкенды на разреженных полосах разбирают пути на каждом вызове заливки, поэтому «кэша фрагментов» (готовых закодированных кусков сцены) нет: кэшируется то, что строится до бэкенда.

1. Отсечение невидимого — обходом дерева сцены по границам поддеревьев: поддерево вне вьюпорта отбрасывается целиком, порядок отрисовки сохраняется без сортировки. R-tree сцены служит hit-testing и запросам по рамке. Обход без рекурсии: глубина дерева из файла не ограничена.
2. Список отрисовки узла: описание формы и краски в локальных координатах и контуры (`BezPath`) формы и колец обводок. Строится при первом полном рисовании и живёт до изменения `version` узла (перемещение и камера его не трогают); контуры узла, не рисовавшегося 300 кадров, выбрасываются. Обводки inside/center/outside — кольца, заливаемые по even-odd, без слоёв с маской; непрозрачная заливка с непрозрачной внутренней обводкой — две заливки вместо заливки и кольца.
3. LOD: поддерево меньше 0.5px не рисуется; узел меньше 3px — прямоугольником цвета первой видимой заливки, без списка отрисовки.
4. Растровый кэш фреймов верхнего уровня при сильном отдалении — включён (бенчмарк показал необходимость: 100 000 прямоугольников LOD стоят ~9 мс): при масштабе устройства ≤ 0.25 контейнер верхнего уровня не больше 256 px рисуется из растра с плотностью — ближайшей степенью двойки не меньше масштаба; растр годится, пока масштаб не упадёт вдвое, и устаревает по `subtree_version`. За кадр строится не больше 32 растров, остальные фреймы рисуются узлами. Только для бэкендов, умеющих изображения (`vello_gpu` — с этапа 4).

### 8.5 Фреймы, прозрачность, изображения, цвет

- `clipContent` → обрезка путём формы фрейма (`push_clip_path`, без слоя композиции); пропускается, если фрейм не повёрнут, без скругления и все дети внутри него.
- `opacity < 1` у контейнера → слой; у листовой фигуры прозрачность умножается в цвет.
- Изображения: рендер получает готовые картинки от поставщика по хэшу; режимы «заполнить», «вписать», «плитка». В worker'е картинка документа декодируется (PNG) при первом запросе рендера, не больше двух за кадр, и живёт в кэше с пределом 256 МБ и LRU-вытеснением; на GPU — в атласе по ключу blake3 (8.1). Пока картинки нет — заглушка; картинка без байтов или неразборчивая — постоянная заглушка. JPEG/WebP через `createImageBitmap` и уменьшенные версии под текущий зум — позже.
- Цвет sRGB. Display P3 — позже.

### 8.6 Оверлеи

В той же сцене vello поверх содержимого, в экранных пикселях: рамки выделения, ручки (8px), подсветка наведения, рамка выделения мышью, линии привязки, пиксельная сетка (зум ≥ 800%), названия фреймов, бейдж «W × H», измерения с Alt (раздел 7.3): отрезки в мире, которые редактор отдаёт в `Overlay.measurements` (расстояние со значением или направляющая), рисуются сплошной линией в 1 px (только видимая часть) с плашкой значения по середине видимой части, целиком на экране, и пунктиром в 1 px (штрих 4 px, промежуток 3 px; строятся только штрихи у экрана) — размеры экранные, от зума не зависят. Тонкие линии выравниваются по пикселям. Подписи — однострочный текст: раскладка `parley` со встроенным шрифтом Onest (SIL OFL), глифы — заливка контуров из `skrifa` через тот же трейт бэкенда (`glyph_run` в `vello_gpu` требует ресурсов рендерера с устройством). Бейдж пока набран Onest с цифрами одинаковой ширины. Цвета — из дизайн-системы (`select`, `on-select`, `component`, `ink-muted`; тёмная и светлая темы). Измерения — цвет `measure` = `danger` (#ff7a7a в тёмной, #c22c2c в светлой), текст их плашек — `on-select`; плашка — та же, что у бейджа «W × H». Совпадение цветов оверлеев с `theme.css` проверяет модульный тест интерфейса.

### 8.7 Экспорт

PNG фрейма или выделения в @1x/@2x/@3x тем же рендером (`vello_cpu`); размер пиксель в пиксель (фрейм 393×852 @3x → 1179×2556), сторона не больше 16384 px. Рисуется только поддерево узла: прозрачность и обрезка предков не применяются. SVG и PDF — подсистема 3, этап 5 (спека `2026-10-29-ferrum-vectors-text-design.md`, раздел 11); в десктопе любой экспорт сохраняется родным диалогом.

## 9. Интерфейс (apps/web)

Раскладка как в Figma UI3; внешний вид — дизайн-система Ferrum (свои цвета, иконки, шрифт): токены `tokens.json` с точными значениями, тёмная тема основная, светлая равноправная, «как в системе» — по `prefers-color-scheme`. Шрифты Onest и JetBrains Mono вшиты в бандл (работают без сети и в Tauri). Иконки до своего набора — формы Lucide (ISC), вставленные разметкой SVG. Стенд ядра этапа 4 — отдельная страница `debug.html` для тестов.

- **Левая панель:** шапка файла («Назад к файлам», имя — двойной щелчок, Enter или F2 переименовывают и запись в хранилище тоже; меню: «Новый файл», «Открыть…» (импорт с диска в хранилище), «Сохранить» (Ctrl/Cmd+S), «Сохранить копию на диск…», «Все файлы», «Настройки…»; «Новый файл» и «Открыть…» не спрашивают — текущий файл сначала сохраняется в хранилище, затем открывается другой); страницы (сворачиваемые; добавить, переключить, переименовать, удалить — с подтверждением, потому что операции со страницами не отменяются); дерево слоёв — виртуализировано (основной поток запрашивает у worker'а только видимые строки с запасом, DOM-строки переиспользуются по месту), переименование на месте (одно поле для файла, страницы и слоя: Enter и уход фокуса применяют, Esc отменяет, фокус возвращается к строке; поле, убранное посреди набора, применяет набранное), перетаскивание для порядка и вложенности (над, под, внутрь фрейма или группы; положение на экране сохраняется; переносится взятое при нажатии, клавиши во время жеста не действуют, Esc отменяет), скрыть и заблокировать, поиск, наведение подсвечивает узел на холсте, выделение синхронно в обе стороны (выделение с холста раскрывает предков и прокручивает к строке).
- **Нижний плавающий тулбар по центру:** перемещение, фрейм с пресетами, фигуры (выпадающий список: прямоугольник, эллипс, линия, изображение; на кнопке — последняя выбранная). Перо, текст, комментарии — отключены с подсказкой, когда появятся.
- **Правая панель:** сверху зум (выпадающий список масштабов) и «Поделиться» (неактивна до подсистемы 4); вкладки «Дизайн» и «Прототип» (вторая неактивна). Секции «Дизайн»: Фрейм/Положение (пресет размера одним шагом, X/Y/W/H, поворот в `(-180, 180]`, отразить) → Вид (прозрачность, радиус, обрезка) → Заливка → Обводка → Экспорт (1×/2×/3×, PNG). Без выделения — фон страницы и экспорт страницы. Значения и «Смешанные» сводит worker; у группы X/Y/W/H — рамка детей, W/H масштабируют детей.
- **Поле числа:** выражения (`120+16`, `50%`, `*2`), у «Смешанных» `+N` — прибавка к каждому; Enter применяет, Esc откатывает, стрелки — шаг; перетаскивание подписи (Shift ×10, Alt ×0.1) — превью и один шаг отмены. Правка без изменений шага не создаёт.
- **Палитра цвета:** HSB, тон, прозрачность, HEX, прозрачность в процентах, пипетка (`EyeDropper` API, где доступен; иначе кнопки нет). Движение в палитре — превью и один шаг; Esc — отмена. Фон страницы во время жеста меняется только в кадре, в документ — при отпускании.
- **Настройки:** горячие клавиши (раздел 7.6), тема, привязка к пикселям.
- **Экран файлов** (этап 6, часть 1; как «Recents» в Figma): маршруты в адресе после `#` — `#/` «Недавние» (по времени открытия), `#/drafts` «Черновики» (все файлы по времени изменения), `#/trash` «Корзина», `#/file/<id>` — редактор с файлом, `#/new` — новый файл в хранилище («Без названия», одинаковые имена допустимы) с заменой адреса на `#/file/<id>`; назад и вперёд браузера работают, неизвестный id — экран файлов с уведомлением «Файл не найден», файл из корзины — «Файл в корзине — восстановите его, чтобы открыть», файл, открытый в другой вкладке, — «Файл открыт в другой вкладке» (см. раздел 10). Отказ уйти назад или вперёд возвращает на свою запись истории одним ходом `history.go` (номер записи в `history.state`), без лишних записей; переходы, пока открыт вопрос об уходе, только запоминаются — решает ответ. Экран файлов не запускает worker ядра (и заставку убирает сразу; у редактора она держится не меньше 2 с); редактор запускает ядро как раньше и останавливает (`dispose`) при уходе после сохранения. Не удалось сохранить (ядро остановлено, снимок или запись не прошли) — вопрос «Изменения не сохранены — уйти?» с причиной, «Остаться» по умолчанию. Боковая панель: знак, «Поиск» (по имени без учёта регистра), разделы — listbox, стрелки переключают. Шапка: название раздела, «Импорт…» (выбор `.ferrum` → новая запись → открыть; файл уходит worker'у ссылкой `Blob`), «Новый файл» (основная), «Сетка / Список» (radiogroup; поле `filesView` настроек `ferrum.settings.v1`, без него — сетка). Карточка (`radius-lg`, отступы экрана — `space-8`): превью (`object-fit: contain` на `canvas` темы, без превью — заглушка), имя с многоточием, «Изменён 5 минут назад» (`Intl.RelativeTimeFormat('ru', {numeric: 'auto'})`, до минуты — «только что»); наведение — рамка, выбор — рамка `select`, фокус — кольцо; щелчок (и по имени — с задержкой 250 мс, чтобы распознать двойной) и Enter открывают, двойной щелчок по имени, F2 и пункт меню переименовывают (`RenameInput`), Delete — в корзину (фокус — на следующую карточку); правый щелчок, Shift+F10, клавиша меню и кнопка «…» (только для мыши: внутри option нет вложенных элементов управления; `aria-setsize`/`aria-posinset` — по всему списку) — меню «Открыть», «Открыть в новой вкладке», «Переименовать», «Скачать копию (.ferrum)», «Удалить»; в корзине — «Восстановить», «Удалить навсегда» и «Очистить корзину» (с `ConfirmDialog`). Список — строки с маленьким превью, именем, «Изменён …» и размером («1,2 МБ»). Пусто — «Здесь пока нет файлов» и «Новый файл», пустой поиск — «Ничего не найдено», пустая корзина — «Корзина пуста». Список виртуальный: основной поток просит у worker'а ввода-вывода окно видимых записей (≤ 200), DOM не растёт с числом файлов; один Tab на весь список, стрелки ходят по сетке (вверх и вниз — на число столбцов). Другая вкладка с экраном файлов видит изменения через `BroadcastChannel('ferrum-files')`. Где есть File System Access (Chrome, Edge) и в десктопе — «Открыть с диска…» рядом с «Импорт…» и в меню файла, там же «Сохранить на диск…»; карточка файла на диске — «На диске · Изменён …»; файл на диске без доступа (браузер перезапущен) открывается после вопроса «Разрешить доступ к файлу на диске?».

- **Доступность:** фокус с клавиатуры — кольцо `select` 2px (`:focus-visible`); роли toolbar, tree, tablist, listbox, menu, dialog, radiogroup (масштаб экспорта: одна точка Tab, стрелки выбирают); стрелки, Home/End, Delete и Backspace идут редактору только с холста (или без фокуса) — на кнопках и полях панелей они не двигают и не удаляют выделение; модальный диалог держит фокус и возвращает его; контраст текста — как в дизайн-системе; `prefers-reduced-motion` выключает анимации.

Дизайн-система обновляется под эту раскладку: компонент Toolbar переделывается в нижний плавающий, добавляются шапки панелей. Секция с прозрачностью называется «Вид» (в README дизайн-системы — «Слой»).

## 10. Хранение файлов

- Интерфейс `FileStore` (TypeScript, `apps/web/src/ui/file-store.ts`) с реализациями: IndexedDB (браузер), File System Access API (Chrome/Edge), Tauri (диск). Серверное хранилище добавится в подсистеме 4 как ещё одна реализация того же формата.
- **Сделано (этап 6, часть 1):** реализация IndexedDB. Вся работа с базой — в worker'е ввода-вывода (`worker/io.worker.ts`); основной поток шлёт запросы и получает метаданные, окна списка и превью. База `ferrum`, версия 1: `meta` (`id`, `name`, `createdAt`, `editedAt`, `openedAt`, `size`, `trashedAt?`, `thumbVersion` — список читает только её), `bytes` (id → `ArrayBuffer` файла `.ferrum`), `thumbs` (id → `Blob` PNG). Метаданные worker держит в памяти: сортировка по разделу, поиск и окна ≤ 200 записей — там. Превью отдаются `Blob`'ами только для видимых карточек, адреса (`URL.createObjectURL`) освобождаются при смене версии, далеко за окном и при закрытии экрана. Запросы к worker'у не доверенные (вид, id ≤ 64 байт, строки ≤ 4096 байт, окно ≤ 200, файл ≤ 512 МБ, превью ≤ 8 МБ). После записи, переименования и удаления worker сообщает своему экрану и другим вкладкам (`BroadcastChannel('ferrum-files')`, там метаданные перечитываются).
- **Путь байтов:** снимок ядра (`Snapshot`) приходит в основной поток передачей буферов (transfer) и тем же способом уходит worker'у ввода-вывода — основной поток байты не копирует и не читает. `MessageChannel` между worker'ами не нужен: ядро живёт только в редакторе и останавливается при уходе, а ошибки записи и снятие `modified` (`MarkSaved` после записи) всё равно проходят через интерфейс. Открытие: worker ввода-вывода читает байты → основной поток (transfer) → worker ядра `Open`; предел — прежний `MAX_COMMAND_BYTES.open`; испорченный файл — экран файлов с сообщением, запись не удаляется.
- **Превью** рендерит ядро в том же снимке: первая страница (текущая сцена, если открыта она; иначе сцена из загруженной страницы или кэша сцены файла), всё содержимое с полем 16 px вписано по центру в 480×320, масштаб не больше 4, фон — фон страницы или прозрачный (под ним — `canvas` темы), путь экспорта PNG с LOD (мелочь — прямоугольниками или пропуском), поэтому время ограничено видимыми в превью узлами: на 100 000 узлах ≈ 49 мс нативно (release) и ≈ 20–40 мс в wasm-worker'е поверх ≈ 450 мс снимка.
- **Две вкладки с одним файлом:** редактор держит блокировку Web Locks `ferrum-file:<id>` (`ifAvailable`), пока файл открыт; вторая вкладка получает экран файлов с «Файл открыт в другой вкладке» — проще и понятнее, чем режим только для чтения, и правки не расходятся. Занятую блокировку редактор ждёт до 1 с (своя прежняя — после F5 или «файлы → тот же файл» — снимается не мгновенно); отказ самого API — экран файлов с «Не удалось открыть файл: блокировка недоступна (…)». Блокировка не защищает метаданные: экран файлов в другой вкладке может переименовать или удалить открытый файл. Имя записи поэтому меняет только `rename` (из экрана файлов или из редактора), запись содержимого его не трогает — автосохранение не откатывает чужое переименование (в открытом редакторе прежнее имя остаётся до следующего открытия). Удалённый навсегда файл не воскресает: запись отвечает «Файл удалён в другой вкладке — сохраните копию на диск» одним уведомлением, документ остаётся изменённым. Запасная защита (нет Web Locks, запись в обход): у записи `version` — поколение содержимого; запись несёт поколение, прочитанное при открытии (`base`), и worker отвечает отказом «Файл изменён в другой вкладке — сохраните копию на диск или откройте файл заново», если файл с тех пор записали. Документ остаётся изменённым — тихой перезаписи нет. Правки записей в worker'е идут по одной и читают запись из базы в той же транзакции, что и пишут (одновременные запись и переименование не откатывают поля друг друга); транзакции записи — `durability: 'strict'`. Превью, которое не удалось построить (нет сцены первой страницы, сбой рендера), не стирает прежнее (`keepThumbnail`); пустая страница — убирает. Имя из хранилища при открытии ставится тихо (`SetDocumentName { quiet }`): открытие — не правка, файл не пересохраняется. «Скачать копию» собирает `Blob` в worker'е ввода-вывода.
- **База (часть 2):** версии 2–4 добавляют хранилища `journal` (`[id, сеанс, пачка]` → пачка журнала), `settings` (поле → значение) и `handles` (id → дескриптор файла на диске и его `lastModified`); хранилища создаются по `contains`, записи версии 1 читаются без переноса.
- **Журнал и автосохранение (часть 2):** правки уходят в журнал не позже 2 с после первой правки (правки подряд пачку не откладывают — после сбоя теряется не больше 2 с правок): ядро отдаёт пачку обновлений Loro за миллисекунды, worker ввода-вывода дописывает её своей транзакцией. Полный файл — через 30 с после последней правки, не реже раза в 5 минут при работе без пауз, по Ctrl/Cmd+S и при уходе; перед снимком ядро отдаёт пачку с правками до него, и она пишется раньше файла, а запись файла стирает пачки до номера снимка — в IndexedDB в той же транзакции (в десктопе — после, см. Tauri). Новый файл без байтов (журнал не к чему применить) до первой записи сохраняется полным файлом через 2 с. Скрыли вкладку — сразу пачка; `pagehide` — пачка и попытка полного файла. «Изменён» значит «не в файле». Пачка, которую ядро не собрало (`failed`), не теряется (те же правки уйдут следующей); пачка, которую не удалось дописать в хранилище, ядром уже отдана — её правки только в памяти, пока их не заберёт полный файл, поэтому до него правки не отодвигают полный файл дальше 5 минут от прошлого. После неудачной полной записи следующая — не раньше чем через 30 с, а не на каждой правке. Ошибка записи — одно уведомление, пока запись снова не удастся.
- **Восстановление (часть 2):** при открытии пачки журнала, записанные после файла, применяются поверх него («Восстановлены изменения, не записанные в файл», документ изменён до следующего полного файла). Повреждённая пачка пропускается целиком, правки без предыдущих не применяются — одно предупреждение. Журнал сверх пределов — файл вместе с ним больше 512 МБ или пачек больше 100 000 — файла не запирает: в браузере и десктопе файл открывается без журнала с одним уведомлением «Журнал изменений слишком большой — файл открыт без несохранённых правок» (хранилище такой журнал не читает: в IndexedDB сначала `count`, в десктопе — подсчёт файлов пачек); первая полная запись стирает его прежние сеансы.
- **File System Access (часть 2, Chrome и Edge):** запись хранилища, связанная с файлом на диске: метаданные, превью и журнал — в IndexedDB, байты — в файле; запись — `createWritable` (браузер подменяет файл целиком при `close`); файл, изменённый другой программой (`lastModified`), — отказ «Файл на диске изменён другой программой…»; нет файла — «Файл на диске не найден…»; доступ после перезапуска браузера — вопрос и `requestPermission` по щелчку. Файл на диске пишется первым (атомарно), затем метаданные и журнал в базе; новое `lastModified` запоминается и при сбое базы, чтобы своя запись не выглядела чужой. «Сохранить на диск…» в файл, уже связанный с другой записью (`isSameEntry`), — отказ «Этот файл принадлежит другой записи Ferrum — выберите другое имя» (как в десктопе): иначе запись затёрла бы единственную копию той. Пачка журнала проверяет запись в той же транзакции: файл, удалённый в другой вкладке, сиротских пачек не получает. «Удалить навсегда» файл на диске не трогает. Изменение файла другой программой ловится только по `lastModified`. Где API нет (Firefox, Safari), пунктов нет.
- **Tauri (часть 2, `apps/desktop`):** хранилище на Rust (`ferrum-desktop-store`): библиотека `library.json` в каталоге данных, новые файлы — в `~/Documents/Ferrum`, открытые с диска остаются на месте; запись атомарная (временный файл → `fsync` → переименование → `fsync` каталога); чужая запись — по поколению и времени изменения файла; журнал — файлы `journal/<id>/<сеанс>-<пачка>.bin`, пачки до номера снимка стираются не в одной транзакции с файлом, а после атомарной замены файла и записи списка (сбой между ними оставит пачку, уже вошедшую в файл, — её повтор безвреден: Loro пропускает известные обновления); превью; настройки в `settings.json`. Открытие читает метаданные, байты файла, сеанс и журнал одной командой под одной блокировкой библиотеки (`files_read_open`), байты забираются по частям сырыми ответами IPC; чтение, запись и пачки журнала окно шлёт по очереди — чтение после перезапуска ядра не встаёт посреди записи прежнего редактора. Ошибки ОС — по-русски («недостаточно места на диске», «нет доступа к файлу или папке», «диск доступен только для чтения», «файл или папка не найдены», прочие — «ошибка диска: » и текст ОС). Приложение одно на библиотеку (`library.lock`): второй экземпляр показывает родным окном «Ferrum уже запущен: библиотека файлов открыта в другом экземпляре» и выходит. Команды IPC, берущие библиотеку или диск, асинхронные (не в главном потоке окна), страница под политикой CSP (`default-src 'self'`, `font-src 'self' data:`, `connect-src 'self' ipc:`), окну выданы пустые разрешения ядра Tauri (`permissions: []`). Родные диалоги «Открыть с диска…», «Сохранить на диск…», «Сохранить копию на диск…» — из Rust (пути интерфейс не видит). В WKWebView страница не изолирована (`crossOriginIsolated === false`) — ядро работает на транспорте postMessage.
- **Сохранение (часть 1, без журнала; заменено частью 2):** полный снимок в хранилище по Ctrl/Cmd+S, через 2 с после последней правки, при уходе на экран файлов или к другому файлу (уход ждёт записи). Ошибка записи (квота и т. п.) — одно уведомление на русском, пока запись снова не удастся; документ остаётся открытым и изменённым, уход отменяется. `pagehide` — попытка сохранить без гарантии: вкладка может закрыться раньше, чем worker допишет. Цена полного снимка: на 100 000 узлах каждое отложенное сохранение держит worker ядра ≈ 0,45 с (холст замирает после паузы в правках) — уйдёт с журналом Loro.
- **Отложено после этапа 6:** быстрое открытие из кэша сцены (первый кадр до раскодирования Loro, правки — после фоновой загрузки): редактор держит загруженную страницу во всех путях (выделение, наведение, панели), а открытие 100 000 узлов уже укладывается в цель (≈ 0,95 с в worker'е при цели 2 с); обновление зеркала страницы по событиям Loro вместо полной перестройки при восстановлении (подсистема 4); SharedArrayBuffer в десктопе (WKWebView не даёт изоляции); вид после перезапуска редактора (страница, камера, выделение); подпись, нотаризация, сборки Windows и Linux, автообновление и меню приложения десктопа; E2E в Safari/WebKit и Firefox в CI. Видимое пользователю из мелочей, оставленных на потом: без Web Locks сжатие журнала в новой вкладке стирает поздние пачки старой; перезапуск ядра на один круг IndexedDB может мигнуть плашкой остановки до уведомления; не ждём возврата контекста WebGL2 дольше двух попыток — медленное восстановление уходит на CPU; щелчок в панели в десятки миллисекунд между отказом GPU и остановкой в файл не попадает (уход спросит); журнал больше 512 МБ или повреждённый остаётся в хранилище и предупреждение повторяется при каждом открытии; пачка журнала только с картинками при восстановлении не применяется; файл раскладки с нестроковой платформой читается как без поля — без предупреждения; отвергнутое запасной записью значение настройки может вернуться при следующем запуске, две вкладки пишут один и тот же ключ — побеждает последняя; сборки Windows и Linux десктопа не проверены, «Удалить навсегда» в десктопе удаляет свой файл сразу, не в Корзину; закрытие окна десктопа не перехвачено (нет `CloseRequested` с записью перед выходом) — выход полагается на `pagehide` в WKWebView, как вкладка браузера: теряется до 2 с правок.

## 11. Обработка ошибок

- Повреждённый файл: открывается всё, что прочитано, с понятным сообщением о потерянном: «Файл повреждён: не удалось прочитать секцию изображений. Документ открыт без 2 картинок» (число — картинки, на которые ссылаются страницы, в нужном падеже), «Файл повреждён: не удалось прочитать страницу «Черновики». Она открыта пустой», «Файл обрезан: часть данных в конце не прочитана»; без корневого документа файл не открывается. Повреждённый журнал — «Не все несохранённые изменения удалось восстановить: журнал изменений повреждён».
- Паника в Rust перехватывается: свой обработчик пишет текст и стек в консоль (`console_error_panic_hook`) и отдаёт текст worker'у до остановки wasm («Ядро остановлено: паника в ядре: …»). После сбоя ядра (паника, исключение в worker'е) тот же файл открывается в новом редакторе с новым холстом, документ — из файла и журнала; уведомление «Редактор перезапущен, изменения сохранены» или, если правки последних секунд не успели в журнал, «Редактор перезапущен. Правки последних секунд не сохранились». Не больше двух перезапусков за минуту на оба вида (сбой ядра и потеря GPU вместе) и не во время открытия файла — иначе остаётся плашка остановки. Перед перезапуском ждут записи отданных ядром пачек, но не дольше 2,5 с (хранилище не отвечает — «Правки последних секунд не сохранились»).
- Потеря GPU-устройства: worker создаёт поверхность того же бэкенда заново на том же холсте (новое устройство WebGPU или восстановленный браузером контекст WebGL2; новый атлас и растры), попытки — сразу и через 1 с, удалось — «Видеокарта перезапущена». Не удалось или поверхность теряется третий раз за жизнь ядра — запасной бэкенд (WebGPU → WebGL2 → CPU): перезапуск редактора с ним (контекст холста выбирается один раз), правки перед этим уходят в журнал; «Видеокарта недоступна — редактор перезапущен с рендером …». Потерянный, не восстановленный контекст WebGL2 рендереру vello не отдаётся (на нём он падает). Каждый текст ошибки WebGPU вне вызовов сообщается один раз; больше 30 таких ошибок — поверхность останавливается с одним сообщением. Кадр больше предела устройства (окно выросло после старта) — одно сообщение и пауза без перерисовки; уменьшили окно — кадры идут снова. Запрос пикселей, пока кадр не показать, получает ошибку.
- Сбой worker'а ядра: одно сообщение «Ядро остановлено: …» с причиной; цикл кадров и пересылка ввода останавливаются, команды получают ошибку «Ядро остановлено, команда не выполнена». Редактор перезапускается (выше); когда перезапуски исчерпаны, интерфейс показывает остановку постоянной плашкой поверх холста: «Ядро остановлено: …» или, если не пережита потеря GPU, «Рендер остановлен: …» (перед этим, пока ядро живо, файл сохраняется полностью, не дольше 5 с; уход с экрана при остановленном ядре ждёт записи не дольше 2,5 с, затем спрашивает о несохранённом).
- Ошибки команд панелей (неверный идентификатор, цвет, слишком длинная строка, последняя страница, неверный файл раскладки) — уведомление на русском; одинаковое сообщение подряд — одно. Запуск, на который worker не ответил за 20 с, отклоняется («Ядро не запустилось: истекло время ожидания»), worker останавливается. Неверное сообщение worker'у (не объект, неизвестный вид, команда не объект) — событие `error`, ядро работает дальше.
- Ошибки пишутся в локальный лог; отправка отчётов — после появления сервера.

## 12. Тестирование

- `ferrum-doc`: тесты мутаций, undo/redo, стабильности `NodeId`, кэша сцены, чтения/записи `.ferrum` и повреждённых файлов; `proptest`: случайные последовательности операций не ломают дерево, зеркало свойств совпадает с честной перезагрузкой из Loro после каждой операции, undo и redo.
- Контрольный бенчмарк `bench_report` (цели из раздела 3) — обязательная проверка этапа 1 и регрессионная проверка в CI.
- `ferrum-editor`: сценарии без браузера (события ввода → проверка документа, выделения и оверлея) для каждого инструмента, правила выделения и модификатора, в том числе точные отрезки и значения измерений с Alt для каждого случая; каждый жест — ровно один шаг отмены, Esc не оставляет истории; тесты таблицы команд, раскладки, конфликтов и формата буфера обмена; `proptest`: случайные последовательности событий не роняют редактор, не оставляют превью после отпускания и Esc, не показывают измерений во время жеста и после потери фокуса, сцена совпадает с построенной заново, отмена каждого записанного шага возвращает документ. Контрольный бенчмарк `editor_report` (цели из раздела 3) — обязательная проверка этапа 3.
- `ferrum-scene`: тесты формы и попадания, сцены и её обновления; `proptest`: после случайных транзакций, undo и redo сцена, обновлённая по `Changes`, совпадает со сценой, построенной заново (вместе с содержимым R-tree).
- `ferrum-render`: эталонные изображения через `vello_cpu` с допуском 3 по каждому каналу (`FERRUM_UPDATE_GOLDEN=1` пересоздаёт эталоны); каждый тест эталона сначала проверяет смысл картинки по отдельным пикселям. Контрольный бенчмарк `render_report` (цели из раздела 3) — обязательная проверка этапа 2.
- Бенчмарки `criterion` на 100 000 и 500 000 узлов с целями из раздела 3; запуск в CI для отлова регрессий.
- `ferrum-wasm`: нативные тесты записей ввода (в том числе `proptest` на произвольных байтах), раскладки общей памяти, сообщений, ядра кадра и картинок; код, которому нужен wasm32 (часы, разбор JS-объектов, кадр без `Instant`), — `wasm-bindgen-test` в Node.
- Интерфейс (этап 5): модульные тесты чистой логики (планировщик, поле числа, цвет, сочетания и таблица раскладки, настройки, буфер обмена, размер картинки по заголовку, пределы интерфейса против констант Rust и `theme-init.js`, цвета оверлеев против `theme.css`, одиночный Alt, тексты отказов) — тем же раннером Playwright без браузера (`npm run unit`); E2E редактора — тулбар, слои и страницы, свойства и отмена, палитра, настройки и раскладка, тема, буфер обмена между страницами, скрытие интерфейса, экспорт PNG, доступность, измерение с Alt (пиксели цвета измерений на холсте, отрезки и значения — тестовой командой `readMeasurements`, фокус после одиночного Alt); бюджет основного потока интерфейса на 100 000 узлах (раздел 3).
- E2E: Playwright (`apps/web/e2e`). С этапа 4 — headless Chromium в двух проектах: как есть (WebGPU нет, WebGL2 — SwiftShader) и с настоящим GPU и WebGPU. Проверяются запуск worker'а, транспорт SAB и запасной postMessage, холст по снимку экрана, ввод и отмена, автовыбор бэкенда, ресайз и dpr, события буфера обмена, пиксели каждого бэкенда против `vello_cpu`, вытеснение из атласа и бюджет основного потока на 100 000 узлах. Проект `gpu` запускает Chromium с флагами Metal (ANGLE Metal, WebGPU) и идёт только на macOS с видеокартой; CI на Linux запускает `npm run e2e:ci` (только проект `chromium`, без замеров `@perf`: на программном рендере общей машины их ворота времени ничего не говорят о коде; локальный полный прогон их включает). Этап 6: круг «нарисовать фрейм → сохранить → перезагрузить → открыть → сравнить» (строки слоёв, свойства, превью байт в байт), журнал (правка в журнале раньше файла, восстановление после перезагрузки, полный файл в простое), сбой ядра (настоящая паника в тестовом режиме, перезапуск, предел), потеря GPU (заглушки пролога worker'а: потеря и возврат контекста WebGL2, потеря устройства WebGPU, запасной CPU с перезапуском редактора), File System Access (файлы OPFS вместо системных диалогов), настройки двух вкладок. Проект `firefox` (тесты `@firefox`: круг сохранения, журнал, отсутствие File System Access) — локально, когда Firefox для Playwright установлен; в CI — нет. Хранилище десктопа — `cargo test` крейта `ferrum-desktop-store`; приложение — проверка запуска `FERRUM_SMOKE=1` (ядро готово в WKWebView, IPC хранилища работает).
