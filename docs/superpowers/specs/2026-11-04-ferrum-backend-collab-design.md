# Ferrum — подсистема 4: бэкенд и совместная работа

Это спека подсистемы 4 из таблицы раздела 1 спеки ядра (`2026-10-23-ferrum-core-design.md`). Архитектура клиента, потоки и протокол ядра — там же. Где спека молчит, решаем как в Figma и помечаем **(поведение)**.

Дата: 2026-11-04.

## 1. Цели

Пользователь может:
- войти по ссылке из письма; без входа редактор недоступен, как в Figma;
- хранить файлы на сервере: «Черновики», команды и проекты;
- поделиться файлом с людьми или по ссылке с ролью «может редактировать» или «может смотреть»;
- править один файл вместе с другими: правки сливаются без конфликтов, видны курсоры, выделения и живое перетаскивание;
- оставлять комментарии на холсте, отвечать, упоминать людей, закрывать обсуждения;
- продолжать правку при потере сети и догонять других при возврате;
- смотреть и восстанавливать версии файла;
- поднять всё одной командой: `docker compose up`.

**Не входит:**
- биллинг, тарифы, квоты по тарифам;
- вход через Google и GitHub: кнопки на экране есть, но неактивны (раздел 5);
- реакции в комментариях, голосовые чаты, «Аудио», Spotlight;
- несколько экземпляров сервера и шардирование: один процесс Bun, но без решений, которые это закрывают;
- обрезка истории Loro на сервере (раздел 7.6).

## 3. Инструменты

- **Сервер:** Bun 1.4, `Bun.serve` с маршрутами и WebSocket, без веб-фреймворка. Postgres через `pg`, один клиент базы на весь сервер. Valkey через встроенный `Bun.RedisClient`. Письма через `nodemailer`.
- **TypeScript 7** (`typescript@7.0.2`) во всём репозитории: сервер с первого коммита, `apps/web` переходит с 6.0.3 в этапе 1. Версии зафиксированы точно.
- **oxlint** и **prettier** во всём репозитории. Конфигурации в корне. Форматирование существующего кода — отдельный коммит только с `prettier --write`, настройки подбираются под нынешний стиль (одинарные кавычки, два пробела). Правила oxlint, которые падают на существующем коде, либо исправляются в этапе 1, либо выключаются с записью в бэклог. Команды: `npm run lint`, `npm run format:check`; Rust не затрагивается.
- **Общий протокол:** пакет `packages/protocol` (только типы и разбор сообщений), его импортируют и `apps/web`, и `apps/server`.
- **Версии Loro:** `loro-crdt` на сервере и `loro` в ядре держатся на 1.16.2 и меняются вместе. Это проверяет тест совместимости (раздел 13).

## 4. Развёртывание

`docker-compose.yml` в корне репозитория, проект `ferrum`:

| Контейнер | Роль | Наружу |
|---|---|---|
| `server` | API, WebSocket, раздача собранного `apps/web` с одного адреса | `8090` (`FERRUM_PORT`) |
| `postgres` | пользователи, файлы, права, журнал обновлений, комментарии | нет |
| `valkey` | сессии, токены входа, ограничение частоты запросов | нет |
| `mailpit` | перехватывает письма в разработке, профиль `dev` | `8025` |

- Образ `server` собирается в несколько стадий: Rust и wasm, затем `apps/web`, затем Bun. CORS не нужен: всё на одном адресе. Заголовки изоляции для `SharedArrayBuffer` ставит сервер, как сейчас `vite preview`.
- Байты снимков, журналов-архивов и картинок лежат на томе `ferrum-data` за интерфейсом `BlobStore { put, get, delete }`. Переход на S3 — новая реализация этого интерфейса.
- Настройки — `.env` (образец `.env.example`): `BETTER_AUTH_SECRET`, `PUBLIC_URL`, `DATABASE_URL`, `VALKEY_URL`, `SMTP_URL`, `MAIL_FROM`, `ALLOWED_EMAILS`.
- Миграции: нумерованные SQL-файлы в `apps/server/migrations`, простая программа применяет их при запуске под блокировкой Postgres. SQL таблиц Better Auth генерируется его инструментом и коммитится как обычная миграция.
- `GET /healthz` проверяет базу и Valkey. Контейнеры ждут друг друга через `healthcheck`.

## 5. Вход (этап 1)

**Better Auth** с зафиксированной версией, таблицы `user`, `account` в Postgres.

- **Magic link:** плагин `magicLink`, срок 15 минут, `storeToken: "hashed"`. Токены и сессии лежат в Valkey через `secondaryStorage` с атомарным `getAndDelete` (`GETDEL`), поэтому ссылка одноразовая.
- **Ссылка не входит сама (поведение):** почтовые сканеры открывают ссылки из писем, и GET-запрос сжёг бы одноразовый токен. Ссылка ведёт на страницу подтверждения с кнопкой «Войти», токен тратится по её нажатию.
- **Сессия:** cookie `HttpOnly`, `SameSite=Lax`, `Secure` при HTTPS, срок 30 дней с продлением. В настройках — выход на этом устройстве и на всех.
- **Регистрация:** первая ссылка создаёт пользователя и его «Черновики». Имя — из экрана первого входа, аватар — цветной кружок с инициалами. `ALLOWED_EMAILS` — список адресов и доменов; если пуст, войти может любой.
- **Обязательный вход:** как в Figma, без сессии открывается только экран входа, запрошенный адрес запоминается и открывается после входа. Открытая ссылка на файл без доступа показывает «Нет доступа» и кнопку запроса доступа.
- **Экран входа:** поле email и кнопка «Получить ссылку»; ниже кнопки «Войти через Google» и «Войти через GitHub» — неактивны, с подсказкой «Скоро». После отправки: «Проверьте почту», повторная отправка через 60 с. Ответ не раскрывает, есть ли такой адрес.
- **Ограничения:** не больше 5 писем на адрес и 20 на IP в час (встроенный `rateLimit`, счётчики в Valkey).
- **Защита:** проверка `Origin` на всех изменяющих запросах и при открытии WebSocket, `trustedOrigins` из `PUBLIC_URL`, проверка входных данных по схемам из `packages/protocol`.

- **Сделано (этап 1):**
  - Инструменты: корневой `package.json`, TypeScript 7.0.2 (и в `apps/web`), oxlint 1.89.0, prettier 3.9.10, `.prettierrc` под нынешний стиль: одинарные кавычки, ширина 140 (самая маленькая правка старого кода из 100–140). Форматирование — отдельный коммит. `no-unassigned-vars` выключено: ссылки SolidJS присваиваются разметкой (B-189).
  - Сервер: `apps/server` на `Bun.serve`, нумерованные миграции под `pg_advisory_lock`, `FsBlobStore`, `/healthz`, заголовки изоляции и CSP как в окне десктопа. `packages/protocol` — разбор запросов входа без зависимостей. Образ в три стадии, `docker-compose.yml` и свой стенд тестов `docker-compose.test.yml`. Порт Mailpit открыт только на `127.0.0.1`: в письмах ссылки входа, а у его веб-интерфейса нет пароля.
  - Better Auth 1.7.16 с `pg` и `Bun.RedisClient`: круг письмо → подтверждение → одноразовость (`GETDEL`, проверено пятью параллельными нажатиями) → сессия в Valkey → проверка сессии работает на Bun без обходов. Токен в Valkey — хэшем, срок 900 с. Таблицы — только `user`, `account`. Valkey сервер переживает: после простоя клиент возвращается сам, на время простоя запросы получают ошибку сразу, а не виснут.
  - **(поведение)** Наружу открыт короткий список маршрутов: `POST /api/auth/{sign-in/magic-link, confirm, confirm-info, name, sign-out, sign-out-everywhere}`, `GET /api/auth/session`; остальные точки Better Auth, в том числе GET, тратящий токен, отдают 404. `confirm` принимает токен в теле и проверяет `Origin`. Ответы не содержат токена сессии: Better Auth отдаёт его в теле, что обесценило бы `HttpOnly`.
  - **(поведение)** Ссылка: `PUBLIC_URL/#/auth/confirm?token=…&next=…`. Токен после `#` не попадает на сервер и в журналы; `next` — только маршрут приложения, поэтому возврат работает и в другом браузере, и не уводит на чужой адрес. Открытие страницы токен не тратит. **(поведение, этап 2, B-193)** Страница делает два запроса: `GET session` и `POST confirm-info` (чей адрес, токен не тратится). «Войти» недоступна, пока не пришли оба. Ссылка другого человека поверх живой сессии спрашивает «Войти как…» или «Остаться»; адрес неизвестен, а сессия есть — предупреждение, что вход может заменить текущий. «Остаться» ведёт на `#/` и не исполняет `next` присланной ссылки. Цена решения: сканер со скриптами видит адрес получателя в странице. Остаток атаки входа по чужой ссылке — B-261. Истёкшая и использованная ссылка неразличимы: «Ссылка недействительна или устарела. Запросите новую». При сбое сети на странице подтверждения «Войти» остаётся повтором, токен в адресе цел; таймаут запросов к серверу 15 с. При сбое сервера (5xx) токен мог быть уже потрачен: Better Auth снимает его до обращения к Postgres, и повтор ответит «Ссылка недействительна». Поэтому рядом с «Войти» — «Запросить новую ссылку». Ссылка, вставленная в ту же вкладку (`hashchange`), тоже работает: при открытом приложении редактор сначала дописывает файл (протокол ухода), затем страница перезагружается.
  - **(поведение)** Предел на адрес — свой счётчик в том же Valkey: встроенный `rateLimit` считает только по IP и пути. Сверх предела — 429 и «Слишком много запросов». Счётчик считается и для адресов вне `ALLOWED_EMAILS`, поэтому по ответу список не раскрывается: такой адрес получает тот же ответ, письма нет. Письмо уходит без ожидания ответа SMTP; письмо собирается и отправляется после ответа (`setTimeout(0)`); сбой отправки пишется в журнал (только `code` и `responseCode`: текст ошибки SMTP содержит адрес). Адрес приводится к нижнему регистру.
  - **(поведение)** IP — адрес соединения. `X-Forwarded-For` учитывается, только если соединение пришло от адреса из `TRUSTED_PROXIES` (точные адреса и IPv4 CIDR, `::ffff:a.b.c.d` — это IPv4, `0.0.0.0/0` не принимается): идём по заголовку справа и берём первый адрес не из списка; все из списка или мусор — адрес соединения. Порт по умолчанию только на `127.0.0.1` (`FERRUM_BIND`).
  - **(поведение)** Проверка сессии вне предела Better Auth: общий IP не закрывает приложение вошедшим. Остальные маршруты — с пределом (B-194).
  - **(поведение)** Сроки: `Pool` — подключение 3 с, запрос 5 с на базе и 6 с на клиенте; весь обработчик `/api/auth/*` — 10 с, затем 503 `UNAVAILABLE`. Это меньше 15 с клиента, поэтому человек видит ответ сервера, а не обрыв. Любой 5xx клиент показывает как сбой сервера. Работа после срока не отменяется: подтверждение может войти в базу, а cookie браузер не получит. Миграции идут отдельным соединением без сроков.
  - **(поведение)** Вход поверх прежнего входа в этом браузере снимает прежнюю сессию (`confirm`, из пришедшей cookie): заменённую cookie из интерфейса уже не снять. Другие устройства этого человека не затрагиваются.
  - Статика: `ETag`, `Last-Modified` и 304, шрифты не качаются заново; `\0` в пути — 404; `immutable` только у настоящих файлов `assets/`. `PUBLIC_URL` сводится к origin, путь, запрос, фрагмент и учётные данные — отказ при запуске. HSTS на год при `https://`, без поддоменов. Без Valkey запуск пишет строку в журнал и выходит через 30 с.
  - **(поведение)** Вход и выход видны в других вкладках (`BroadcastChannel`), вкладка «Проверьте почту» открывается сама. Выход есть и на экране файлов: настройки открываются только из редактора. Выход из редактора проходит протокол ухода: «Остаться» отменяет выход, другие вкладки дожидаются записи файла и перезагружаются. Смена адреса и сбой фонового обновления не сбрасывают экран входа и экран имени; в письмо уходит адрес на момент отправки.
  - «Черновики» отдельной записи не требуют: по §6.1 это файлы с пустым `project_id`, создавать при регистрации нечего.
  - Рабочая сборка: `npm run build:server` в `dist-server`, без `debug.html`, код входа подключает ветка `main.tsx` через `extensions.ts`; ссылку подтверждения `Root` пропускает по `extensions.ownsHash`, и в автономной сборке любой адрес — его, `#/auth/foo` ведёт на экран файлов; `check-dist.mjs` проверяет обе сборки. `npm run build` и `npm run dev` — автономный режим (`.env.standalone`), десктоп собирает его через `beforeBuildCommand`. Файлы в обеих сборках пока в IndexedDB, общие для всех, кто входит в этом браузере (B-190).
  - `authorizeUpgrade(req, auth, publicUrl)` — проверка `Origin` и сессии для WebSocket этапа 3, тест — настоящий upgrade на Bun.
  - Тесты: `bun test` против Postgres, Valkey и Mailpit в Docker; Playwright `playwright.server.config.ts`, проекты `server` и `server-firefox`. Отдельный конфиг, чтобы обычному `playwright test` Docker не требовался.

**Автономная сборка.** Флаг времени сборки `VITE_FERRUM_LOCAL=1` оставляет прежний режим без сервера, с локальным `FileStore`. Рабочая сборка кода автономного режима не содержит. Он нужен для 416 E2E и для работы над редактором без Docker. Новые сценарии проверяются отдельным проектом Playwright против настоящего стенда.

## 6. Файлы на сервере (этап 2)

### 6.1 Модель

```
team(id, name, created_at)
team_member(team_id, user_id, role: owner | member)
project(id, team_id, name)
file(id, owner_id, project_id?, name, created_at, edited_at, trashed_at?, thumb_key?, schema_version)
file_access(file_id, user_id, role: owner | editor | viewer)
share_link(file_id, token_hash, role: editor | viewer, enabled)
file_image(file_id, hash)
image(hash, size, blob_key)
```

- `project_id` пуст — файл в «Черновиках» владельца.
- **Действующая роль (поведение, как в Figma):** наибольшая из прямой, роли по ссылке и роли через команду. Участник команды — `editor` на файлах её проектов.
- Читатель (`viewer`) видит файл, курсоры и может комментировать, но не правит. Экспорт читателю разрешён, как в Figma по умолчанию.

### 6.2 Экран файлов

Разделы: «Недавние», «Черновики», команды и их проекты, «Доступные мне», «Корзина». Вся логика — окна списка до 200 строк, как сейчас (спека ядра §10), только источником становится сервер. Новая реализация `ServerFileStore` того же интерфейса `FileStore`. Превью по-прежнему рендерит ядро, клиент загружает его отдельным запросом не чаще раза в минуту. Команду создаёт любой пользователь; участники приглашаются по email со страницы команды.

### 6.3 «Поделиться»

Кнопка в шапке редактора: приглашение по email с ролью, список людей, смена и снятие роли, ссылка с ролью и выключателем. Токен ссылки в базе хранится хэшем. Снятие роли мгновенно закрывает соединение этого человека с файлом, а открытый редактор показывает «Нет доступа» (до этапа 3 — см. «Сделано (этап 2)»). Понижение до читателя переводит открытый редактор в режим просмотра без перезагрузки.

### 6.4 Картинки

Адресация по blake3, как в файле. Клиент сначала загружает картинку (`PUT /files/:id/images/:hash`, сервер проверяет хэш и размер), затем отправляет правку со ссылкой на неё. Загрузка идёт в worker'е ввода-вывода. Чтение — с проверкой доступа к файлу через `file_image`. Неиспользуемые картинки удаляются фоновой задачей через 30 дней.

### 6.5 Локальные файлы

- **Импорт:** «Открыть с диска» создаёт копию `.ferrum` в «Черновиках» (поведение: как `.fig` в Figma). Связь записи с файлом на диске через File System Access в рабочей сборке снимается.
- **Экспорт:** «Сохранить копию на диск» пишет обычный `.ferrum`, он открывается и в старых сборках.
- **Файлы из IndexedDB:** если у браузера есть файлы прежней версии, экран файлов показывает «Локальные файлы (N)» с переносом на сервер по одному или все сразу. Оригинал остаётся, пока его не удалят.
- До этапа 3 файл пишется целиком, как сейчас, с проверкой поколения (`CONFLICT`). Этап 3 заменяет это журналом.

- **Сделано (этап 2):**
  - **Модель.** Сверх §6.1: `file.version`, `size`, `content_key`, `thumb_version`, `last_write_id`, `trashed_by`; `file_recent` (открытия у каждого свои), `file_invite` и `team_invite` (адрес без учётной записи), `file_link_user` (кто пришёл по ссылке), `share_link.nonce`, `image.orphaned_at`, `file_image.unreferenced_at`, `blob_trash`, `blob_pending` (намерение загрузки: запись появляется до первого байта и снимается транзакцией фиксации, очистка переносит оставшиеся старше 24 ч в `blob_trash`; загрузка дольше 24 ч получает при фиксации 503 `UNAVAILABLE`). Сбой процесса между загрузкой и фиксацией байтов не оставляет. Действующая роль — функция базы `file_role_rank`. Адреса API — `/api/files/…`, `/api/teams/…`, `/api/projects/…`: один префикс с входом и прокси разработки.
  - **Конвейер маршрутов** (`api.ts`): `Origin`, сессия, предел частоты, права, срок и ответ в формате ошибок — у каждого маршрута, обработчик этого не делает. Нет доступа — 404, как у несуществующего; роли не хватает — 403. `Access.member` у маршрута: мало роли по ссылке или за отметку «убрал», нужна прямая или через команду (`file_member_rank`, на ней построена `file_role_rank`). 429 несёт `Retry-After`: у предела частоты — остаток окна, у занятых слотов (`BUSY`) — 5 с. Ответы `content`, `thumb` и `images` — с `Cross-Origin-Resource-Policy: same-origin`.
  - **Обрыв соединения с базой.** У каждого клиента пула есть слушатель `error` с рождения, поэтому обрыв занятого соединения не роняет процесс: запрос получает 503, пул заводит новое соединение. Valkey отвечает отказом команды, клиент подключается сам.
  - **Смена входа (поведение).** Cookie общая на браузер, поэтому worker файлов подписывает запросы заголовком `x-ferrum-user`, а сервер при расхождении с сессией отвечает 401. Вкладка X под cookie Y не записывает правки X и не снимает плашку опросом, хотя у Y может быть право на файл; правки X остаются в его журнале. Вернулся тот же человек — опрос снимает плашку.
  - **Запись файла целиком** идёт потоком на диск и обратно; в памяти только текущий кусок. Поколение и роль проверяются в транзакции фиксации, а заведомый отказ — раньше передачи. Сервер ходит по заголовкам контейнера, не раскодируя документ. **(поведение)** Запись несёт свой номер: своя удачная запись, ответ на которую потерялся, не становится `CONFLICT`. Байты заменённого файла удаляются через 2 минуты, читатель успевает дочитать.
  - **Пределы записи.** Клиент заранее отказывает в записи больше 512 МБ вместе с картинками (`TOO_LARGE`, до передачи; сервер считает файл без картинок, а открыть такой файл потом было бы нельзя), прежнее содержимое остаётся, правки в журнале браузера. Разных картинок в файле не больше 10 000 (`MAX_IMAGE_REFS`, сервер: 400 `TOO_MANY_IMAGES`): память записи постоянна. Загрузок одновременно 8 на человека и 32 на сервер (429 `BUSY`). **(поведение)** Загрузка, отстающая от 32 КиБ/с в среднем после минуты форы, получает 408 и освобождает слот; простой дольше минуты — то же. Клиентский срок передачи — от 64 КиБ/с без верхней границы, поэтому 512 МБ на медленном канале доходят, хотя и за часы.
  - **Договор картинок и записи (поведение).** Запись со ссылкой на картинку, которой нет у файла, получает 409 `MISSING_IMAGES`: порядок «сначала картинка, потом правка» обязателен. Заголовок `x-ferrum-lost-images: N` объявляет ссылки, байтов которых нет и у клиента (потеряны раньше): правки из-за них не застревают, ядро покажет заглушку. Проверка считает количество, а не хэши (B-294). Клиент при `MISSING_IMAGES` сбрасывает кэш известных картинок, догружает и повторяет один раз.
  - **Автоповтор записи (поведение).** Неудачная запись через сеть повторяется сама: 30 с, 1, 2, 5, затем каждые 10 минут; удача или новая правка начинают сначала. Не повторяются `CONFLICT`, `FORBIDDEN`, `NOT_FOUND`, `UNAUTHORIZED`, `TOO_LARGE`, `BAD_CONTAINER`, `BAD_REQUEST`, `HASH_MISMATCH`, `TOO_MANY_IMAGES`. Закрытие вкладки спрашивает, пока правки есть только в памяти или пачка журнала ещё дописывается.
  - **Запись в файл в корзине (поведение).** Запись содержимого, имени и превью разрешена владельцу файла в корзине: файл не закрывается у того, кто его только что убрал в другой вкладке, правки не теряются. Открыть файл из корзины нельзя, сначала восстановить.
  - **Полные снимки уже здесь (§7.6).** `Snapshot { full }`: проба показала, что журнал отставшей вкладки shallow-снимок не принимает, а полный — сливает. 100 000 узлов: 33,3 МБ, запись через сервер около 4 с, открытие около 0,8 с, длинных задач на основном потоке нет. **(поведение)** После `CONFLICT` правки не теряются: они в журнале браузера и сливаются при следующем открытии файла. Исключение — файл без записи (следующий пункт). «Скачать копию» с экрана файлов отдаёт байты сервера: полная история и кэш сцены, удалённое остаётся в копии, которую человек передаст дальше. «Сохранить копию на диск» из редактора — shallow только у открытых страниц, неоткрытые пишутся как прочитаны, с историей (B-295).
  - **Файл без записи, который записал другой (поведение).** X создал файл и позвал Y, Y открыл его пустым, X записал первым. Журнала у Y нет (пачки у незаписанного файла не ведутся), а документы независимы: корни разные, слить нечего. Запись Y получает `CONFLICT`, редактор переходит в просмотр и больше не пробует писать, опрос плашку не снимает. Плашка и вопрос при уходе говорят, что правки пропадут, и предлагают «Сохранить новым файлом» (файл «<имя> (копия)» в «Черновиках», редактор переходит в него) и «Сохранить копию на диск».
  - **Журнал правок** — в браузере, своя база на человека (`ferrum-user-<id>`). Читатель его не применяет и не стирает: журнал ждёт, пока вернут право, тогда файл открывается заново. Запись на сервер снимает пачки после ответа сервера, а не одной транзакцией: сбой между ними оставит пачки, открытие применит их поверх файла без вреда.
  - **Картинки** не лежат в файле на сервере: worker выносит их перед записью и вставляет обратно при чтении, ядро получает обычный контейнер, хэш секции — её имя. `file_image` появляется только у того, кто прислал все байты: знание хэша ничего не даёт. **(поведение)** Ссылка без употребления в файле живёт 30 дней (отмена может её вернуть), затем ещё 30 — запись картинки без файлов: байты неиспользуемой картинки живут до 60 дней. Запрос картинки — свой предел частоты, 6000 в минуту на человека: файл на 1200 картинок открывается, 600 новых переносятся, проверено на стенде. Сверх предела клиент ждёт `Retry-After` (до 6 попыток) и только потом показывает «Слишком много запросов», а не «Нет связи».
  - **Роли (поведение).** Участник команды — редактор файлов её проектов, владелец команды — владелец. Файлы ушедшего участника переходят владельцу команды. Редактор может приглашать и повышать читателя, менять и снимать роли — только владелец; снять себя может редактор, у читателя номера записи нет (B-289). Ссылка не даёт звать людей и видеть их адреса: `GET share`, `invite`, `PATCH people`, `PUT link`, `link/reset` отвечают 403 пришедшему только по ссылке и тому, кого держит только отметка «убрал». Кнопка «Поделиться» показывается по `canShare` из ответа `GET access`, а не по роли: у читателя и редактора по ссылке её нет (в Figma есть). В корзину убирает только владелец, файл из корзины виден только ему и тому, кто убрал. Файлы ушедшего участника передаются вместе с `trashed_by`: он не видит и не очищает корзину с ними. Нельзя удалить команду с проектами и проект с файлами. Удаление команды и проекта и снятие участника — с подтверждением.
  - **Приглашения (поведение).** Приглашения на адрес становятся доступом при каждом входе (`session.create.after`, в том числе первом): запись, вставленная в гонке с прошлым входом или при сбое, перейдёт при следующем; у существующего человека запись убирается транзакцией. Список не выдаёт, есть ли учётная запись: имя появляется, когда человек открыл файл, в команде — только адреса. На почтовый ящик не больше 5 приглашений в час: счётчик без метки `+…` и точек, поэтому `box+1@d` и `b.ox@d` его не обходят; сверх предела и вне `ALLOWED_EMAILS` запись остаётся, письма нет, ответ тот же. Адрес — без отображаемого имени, комментариев, списков и маршрутов почты (`x<box@d>`, `z,box@d`, `(c)box@d`, `q:box@d;` отвергаются, в том числе при входе), письмо уходит только на проверенный адрес. Запрос доступа, чьё письмо съел предел, можно повторить, а не ждать сутки.
  - **Ссылка (поведение).** Токен в базе хэшем, а показать его можно снова, как в Figma: он выводится из секрета сервера и `nonce`. Роль по ссылке действует, пока ссылка включена; новая ссылка отменяет прежнюю и всех пришедших по ней. `redeem` на файле в корзине даёт 404 и записи не создаёт: после возврата файла токен предъявляют снова. Токен уходит из адреса после ответа `redeem`, до этого он в адресе и записи истории; сбой сети или 429 на `redeem` показываются как «Нет доступа» (B-272).
  - **Расхождение с §6.3.** WebSocket появится на этапе 3, поэтому снятие роли не мгновенно. Опрос несёт ещё `canShare` и `version`, которых нет в `role { role }` §7.2: сообщение придётся расширить или оставить чтение `GET access` (B-296). Запись отказывает сразу и в транзакции; открытый редактор узнаёт при первой записи, при возврате на вкладку или опросом `GET /api/files/:id/access` раз в 15 с. Понижение переводит в режим просмотра без перезагрузки, снятие показывает «Нет доступа» с копией на диск. Этап 3 шлёт `role` и `access-revoked` в тот же обработчик, опрос убирается (B-237).
  - **Экран файлов.** Раздел «Доступные мне», проекты команд в панели, диалог команды. **(поведение)** Страница команды — диалог, а не маршрут. Список перечитывается раз в 15 с, пока вкладка видна. Превью — не чаще раза в минуту. Импорт называется «Открыть с диска…», связи с файлом на диске в рабочей сборке нет.
  - **Сборки.** Хранилище выбирает `main.tsx`. В рабочей сборке нет `TauriFileStore` и тестового доступа, `?debug` там не действует. В автономной нет кода сервера: `ui/server/setup` подменён заглушкой (`vite.config.ts`), иначе сборщик выпускал файл worker'а из мёртвой ветки. Всё это проверяет `check-dist.mjs`.
  - **(поведение)** Выход или вход другим человеком в другой вкладке: редактор пробует записать файл. Вышло — перезагрузка. Не вышло: сессии нет или правки только в памяти (новый файл без записи) — плашка «Сессия завершена», копия на диск, «Войти» задаёт вопрос; пришёл другой человек, а правки в журнале — перезагрузка, они останутся в журнале прежнего. Экран файлов при 401 перезагружается и показывает вход.
  - **Локальные файлы (поведение).** Перенос по одному или все сразу. Журнал сверх предела и файл больше 512 МБ не переносятся, для журнала есть «Перенести без правок» (отметки «перенесён» после неё нет, поэтому можно повторить, B-293). Состояние переноса живёт вне диалога, поэтому двойной клик и закрытие дубля не дают. Сбой `journal.append` откатывает перенос. Перед удалением оригинала подтверждение.
  - Новая зависимость: `@noble/hashes` 2.4.0 — blake3 на сервере, в `Bun.CryptoHasher` его нет.

## 7. Синхронизация (этап 3)

### 7.1 Соединение и данные

- Один WebSocket на открытый файл: `GET /files/:id/sync`, сессия и роль проверяются при открытии. Кадры двоичные, формат — в `packages/protocol`.
- Единица синхронизации — документ Loro файла: корень (`root`) или страница (`pageId`). Клиент подписан на корень и загруженные страницы, остальные подгружаются по требованию, как сейчас.
- WebSocket живёт в отдельном `sync.worker`. С worker'ом ядра он соединён прямым `MessageChannel`, основной поток трафика не видит, буферы передаются (transfer).

### 7.2 Сообщения

| Направление | Сообщение | Смысл |
|---|---|---|
| клиент → сервер | `hello { protocol, schema }` | первое сообщение; несовместимая версия — `please-reload` |
| клиент → сервер | `subscribe { doc, vv }` | подписка с вектором версий клиента |
| клиент → сервер | `update { doc, clientSeq, bytes }` | своя правка |
| клиент → сервер | `ephemeral { bytes }` | присутствие, этап 4 |
| сервер → клиент | `updates { doc, seq, bytes }` | правки других или догоняющая пачка |
| сервер → клиент | `snapshot-needed { doc, url }` | клиент отстал сильнее журнала, скачать снимок |
| сервер → клиент | `ack { doc, clientSeq, seq }` | правка записана на диск базы |
| сервер → клиент | `role { role }`, `access-revoked` | роль изменилась |

### 7.3 Сервер

Сервер не держит документы в памяти на горячем пути:
- **Приём:** `decodeImportBlobMeta` из `loro-crdt` даёт версии начала и конца без загрузки документа. Сервер проверяет роль, размер (до 16 МБ на кадр) и непрерывность по пирам относительно своего вектора документа. При разрыве клиент получает ошибку и присылает правки заново от последнего `ack`.
- **Запись:** пачка попадает в `doc_update(file_id, doc, seq, start_vv, end_vv, bytes)`. Записи собираются группами каждые 20 мс одной транзакцией. `ack` и рассылка другим — только после фиксации транзакции.
- **Рассылка:** правка уходит подписчикам этого документа в том порядке, в каком получила `seq`. Отправителю приходит только `ack`.
- **Догоняние:** по `subscribe { vv }` сервер шлёт записи журнала, конец которых не покрыт `vv`. Если журнал уже сжат дальше — `snapshot-needed`.

### 7.4 Сжатие

Bun Worker с `loro-crdt` загружает снимок и журнал документа, строит новый полный снимок, кладёт его в `BlobStore`, запись о нём и удаление вошедших записей — одной транзакцией. Запуск: больше 2000 записей или 32 МБ журнала, либо через 5 минут после ухода последнего участника. Worker обрабатывает по одному документу и пересоздаётся после каждых 50 задач, потому что память wasm не возвращается системе.

Если обновление не удалось применить при сжатии, снимок не заменяется, журнал документа остаётся как есть, в лог пишется ошибка с `seq`. Рассылка и приём правок при этом продолжаются, а следующая попытка — через час. Автоматически ничего не удаляется.

### 7.5 Открытие файла

`GET /files/:id/content` отдаёт контейнер `.ferrum` той же структуры, что и файл: корень, полные снимки страниц, ссылки на картинки, без кэша сцены. Его собирает Worker сжатия вместе со снимками; `seq` каждого документа передаётся в заголовке контейнера. Ядро открывает его обычным `Open`, затем `sync.worker` подписывается и догоняет журнал. Быстрое открытие: клиент кэширует контейнер с кэшем сцены в IndexedDB (раздел 11).

### 7.6 Только полные снимки

**Проверено на `loro-crdt` 1.16.2:** документ из shallow-снапшота отвергает параллельную правку с ошибкой «The dependencies of the importing updates are not included in the shallow history of the doc», а документ из полного снимка принимает её. Поэтому серверные файлы и их локальная копия хранят полные снимки. Shallow-снапшоты остаются для «Сохранить копию на диск».

Цена — файл растёт с историей правок. Обрезка истории на сервере возможна при условии, что клиент, отставший сильнее границы, скачивает снимок заново, и записана в бэклог. Размеры на реальном файле измеряет этап 3.

## 8. Ядро: чужие правки (этап 3)

- **Новая команда** `ApplyRemote { doc, bytes }`, событие `LocalUpdates { doc, clientSeq, bytes }`. Отправка пачек ядром — не реже 30 раз в секунду, только пока есть правки. Журнал для автосохранения (`take_journal`) и курсор синхронизации считают версии независимо.
- **Обновление зеркала по изменённым узлам:** сейчас `import_updates` вызывает `rebuild_from_loro` и перестраивает индекс и зеркало страницы целиком. Для чужих правок это заменяется подпиской на события Loro: для каждого изменённого узла обновляются запись зеркала, индекс `NodeId → TreeID` и `Changes`, дальше работает обычный путь `take_changes` → сцена. Цель: пачка из одной правки на 100 000 узлов применяется не дольше 2 мс нативно (раздел 13).
- **Выделение:** удалённый другим узел снимается с выделения без сообщения. Перемещение в другого родителя выделение не меняет.
- **Незавершённый жест (поведение):** если узел, который тянут или ресайзят, удалён другим, жест отменяется. Правки остальных свойств жест не прерывают: при отпускании побеждает последняя запись по правилам Loro.
- **Правка текста:** участки сливаются посимвольно через `LoroText`. Каретка и выделение пересчитываются при чужих вставках. Узел удалён другим — сеанс правки закрывается.
- **Правка вектора:** сеть точек — неделимое значение, побеждает последняя запись (поведение). Обновление, изменившее сеть во время её правки, применяется к документу, а сеанс правки вектора закрывается с уведомлением.
- **Отмена (поведение, как в Figma):** отменяются только свои шаги. Шаг над удалённым другим узлом пропускается, и отмена переходит к следующему. Значение свойства возвращается к своему прежнему, даже если его после этого менял другой. История живёт в пределах сеанса, как сейчас.
- **Журнал отмены страниц** не меняется: операции со страницами остаются в корневом документе.
- **Новые версии:** файл с большей `schemaVersion` или неизвестными узлами открывается только для чтения, как сейчас, и показывает «Обновите страницу». Правки от других при этом продолжают применяться.
- **Сессия пира:** `PeerId` случайный на каждое открытие файла, поэтому две вкладки и восстановление после сбоя не пишут от одного пира. Запрет «файл открыт в другой вкладке» для серверных файлов снимается: вкладка — такой же участник.

### 8.1 Состояние соединения

Индикатор в шапке: «Синхронизировано», «Сохранение…», «Нет сети — правки сохранятся при подключении». Переподключение: от 0,5 до 30 с с разбросом, сразу при событии `online`. Правки без `ack` хранятся в журнале IndexedDB и отправляются заново; Loro пропускает уже известные, поэтому повтор безвреден.

## 9. Присутствие (этап 4)

- **Транспорт:** `EphemeralStore` Loro на клиенте, кадры `ephemeral` проходят через сервер без хранения и рассылаются участникам файла. Сервер подписывает их `userId` соединения: чужой курсор подделать нельзя. Предел — 2 КБ на кадр и 30 кадров в секунду на соединение, лишнее отбрасывается.
- **Данные участника:** `userId`, имя, цвет (из хэша `userId`), страница, камера, курсор в мировых координатах, выделение, идентификаторы и преобразования живого превью.
- **Частота:** курсор — до 20 раз в секунду, движение между кадрами плавно интерполируется в ядре.
- **Рисует ядро в том же кадре,** как другие оверлеи (спека ядра §8.6): чужой курсор с подписью, рамка чужого выделения цветом участника, живое превью узлов при перетаскивании, ресайзе и повороте.
- **Шапка:** аватары участников, цвет совпадает с курсором; больше пяти — счётчик со списком. Щелчок — следование за участником: камера и страница повторяют его, синяя рамка окна, любое действие на холсте выходит из следования (поведение). Участники на других страницах в списке есть, курсоров их не видно.
- **Несколько вкладок одного человека:** два участника с одним аватаром; аватар в шапке один (поведение).
- **Ушедший участник** пропадает через 30 с без кадров, при закрытии соединения — сразу.
- **Предел:** курсоры рисуются для 50 участников, остальные только в счётчике.

## 10. Комментарии (этап 5)

### 10.1 Модель

Комментарии живут в Postgres, а не в Loro: они не шаг отмены, не часть документа и не попадают в экспорт.

```
comment_thread(id, file_id, page_id, node_id?, x, y, created_by, created_at, resolved_at?, resolved_by?, seq)
comment(id, thread_id, author_id, body, created_at, edited_at?, deleted_at?)
comment_mention(comment_id, user_id)
comment_read(thread_id, user_id, read_at)
```

### 10.2 Метка на холсте

- **Привязка:** щелчок над узлом привязывает метку к верхнему фрейму или узлу под точкой; `x`, `y` — смещение в координатах этого узла, поэтому метка едет вместе с ним. На пустом месте — мировые координаты страницы.
- **Узел удалён или скрыт (поведение):** метка остаётся там, где он был. Сервер хранит последние мировые координаты, клиент обновляет их при создании и при перемещении метки.
- **Рисует ядро:** круг с инициалами автора, счётчик ответов, отметка «не прочитано». Метки близко друг к другу собираются в группу с числом при маленьком масштабе. Попадание по метке проверяет ядро. Метки не экспортируются и не попадают в превью.

### 10.3 Работа в интерфейсе (как в Figma)

- **Режим:** инструмент «Комментарий» — клавиша C, кнопка в тулбаре, пункт в палитре и в меню «Вид». Shift+C показывает и скрывает метки. В режиме комментариев остальные инструменты не работают, камера работает.
- **Новый комментарий:** щелчок открывает поле. Enter — отправить, Shift+Enter — новая строка, Esc — отмена. Метку можно перетащить автору и владельцу файла.
- **Обсуждение:** окно рядом с меткой, закрывается щелчком мимо. Ответы, правка своего комментария, удаление своего; владелец файла удаляет любые. Удаление первого комментария удаляет обсуждение. Кнопка «Закрыть обсуждение», закрытое можно открыть снова.
- **Упоминания:** `@` открывает список людей с доступом к файлу, поиск по имени и email; упоминание без доступа не предлагается. В тексте хранится `@[userId]`, показывается имя. Текст показывается только как текст, без HTML, до 4000 символов.
- **Панель:** в режиме комментариев правая панель показывает обсуждения: по текущей странице или всем, сортировка по дате или непрочитанным, фильтр «Только мои», показ закрытых. Щелчок — переход на страницу, камера центрируется на метке, открывается окно.
- **Ссылка:** `#/file/<id>?comment=<threadId>` открывает файл на обсуждении; адрес из письма ведёт туда.
- **Права:** комментировать могут все с доступом к файлу, в том числе читатели.

### 10.4 Доставка

- **API:** REST `GET/POST/PATCH/DELETE /files/:id/comments…`, ограничение — 60 комментариев в минуту на пользователя.
- **Живое обновление:** сервер шлёт `comment-event { thread, comment, kind }` по WebSocket файла, клиент обновляет панель и метки без перезагрузки.
- **Письма:** упоминание и ответ в обсуждении, где человек участвует, если он не открыл файл. Письма группируются за 5 минут, в письме есть ссылка на обсуждение. Настройка «Письма о комментариях» в настройках, по умолчанию включена. Очередь — таблица `mail_outbox` в Postgres, чтобы письмо не терялось при перезапуске.

## 11. Офлайн и версии (этап 6)

### 11.1 Офлайн (как в Figma)

- **Локальная копия:** последние 20 открытых файлов, контейнер с полными снимками и кэшем сцены в IndexedDB с разделением по `userId`, выход стирает копии только после отправки неотправленных правок или подтверждения пользователя.
- **Без сети:** открытый файл продолжает работать. Недавние файлы открываются из копии, если сессия была действительна при последней проверке. Сессия с сервера при этом не проверяется, а при возврате сети проверяется; истёкшая — экран входа, правки остаются в журнале и отправляются после входа тем же пользователем.
- **Догоняние:** журнал правок из спеки ядра §10 применяется поверх копии, затем `subscribe` с вектором версий. Параллельные правки сливаются Loro. Файл создаётся без сети как временный, идентификатор — у клиента, сервер принимает его при возврате (идемпотентно).
- **Отозванный доступ:** правки отвергаются, файл можно сохранить как копию на диск или новым файлом в «Черновиках».
- **Service Worker:** статика приложения кэшируется, чтобы страница открывалась без сети.
- Комментарии без сети недоступны и отправляться не будут: поле показывает «Нет сети» (поведение).

### 11.2 Версии

- **Автоматически:** снимок после 30 минут паузы в правках, но не чаще раза в час работы. Ручные: «Сохранить в историю версий» с именем и описанием (Ctrl/Cmd+Alt+S).
- **Хранение:** `file_version(id, file_id, kind, name?, description?, created_by, created_at, frontiers, blob_key)` — полный снимок всех документов файла. Автоматические старше 30 дней прореживаются до одной в день; именованные хранятся всегда (поведение).
- **Панель:** список слева по дням, щелчок показывает версию в режиме только для чтения, не влияя на других. «Восстановить» записывает состояние версии новыми правками поверх текущего — это обычный шаг для всех участников, история не теряется. «Дублировать» создаёт новый файл.

## 12. Десктоп (этап 7)

Вход обязателен и здесь, как в десктопе Figma.

- «Войти» открывает системный браузер. После входа страница выдаёт одноразовый код плагином `oneTimeToken` (срок 1 минута) и открывает `ferrum://auth?code=…`, приложение меняет его на токен сессии.
- Токен хранится в связке ключей ОС и передаётся заголовком `Authorization` (плагин `bearer`). В cookie он не лежит.
- Адрес сервера — в настройках, по умолчанию из сборки. CSP окна дополняется адресом сервера в `connect-src`.
- Локальная библиотека `ferrum-desktop-store` становится источником импорта, её файлы переносятся так же, как файлы IndexedDB (раздел 6.5). Копии для офлайна лежат на диске.
- Проверка входа живьём — вручную автором проекта, как проверка родных диалогов (B-83).

## 13. Цели и тестирование

### 13.1 Цели производительности

| Что | Цель |
|---|---|
| Своя правка видна другому, та же сеть | ≤ 150 мс, p95 |
| Сервер: от кадра до рассылки, 50 участников | ≤ 40 мс, p95 |
| Применить чужую одиночную правку на 100 000 узлов, нативно | ≤ 2 мс |
| Кадр с 50 курсорами, прибавка, 1920×1080 | ≤ 1 мс |
| Открыть файл 100 000 узлов с сервера, из кэша | ≤ 2 с, как в спеке ядра |
| Основной поток при 50 участниках | без длинных задач от синхронизации |

Цели заносятся в `editor_report` и новый `sync_report`. Цифры — ориентиры до первого замера; если цель окажется невыполнимой, это решение выносится в описание PR.

### 13.2 Тесты

- **Совместимость Loro:** обновления и снимки, экспортированные Rust-ядром, импортируются `loro-crdt` на Bun и наоборот; тот же тест ломается при расхождении версий.
- **Сходимость:** случайные правки нескольких клиентов с перестановкой и повтором пачек на уровне `ferrum-doc`; все приходят к одному дереву, зеркало совпадает с полной перестройкой из Loro. Это проверка обновления зеркала по изменённым узлам.
- **Сервер:** `bun test` против настоящих Postgres и Valkey в Docker: вход, одноразовость ссылки, срок токена, ограничение частоты, права на каждый маршрут и на WebSocket (чужой файл, читатель с `update`, отозванный доступ), сжатие с падением посередине.
- **E2E, новый проект `server`:** Playwright против `docker compose` (порты и проект отдельные): письмо читается через API Mailpit, вход, два контекста браузера правят один файл, курсоры, комментарий и упоминание, обрыв сети и возврат (`context.setOffline`), версия и её восстановление. Браузеры: Chromium все сценарии, Firefox основные.
- **Автономная сборка:** существующие E2E и unit идут как раньше.
- **Совместимость файлов:** `scripts/compat-old-build.sh` — экспортированный `.ferrum` открывается старой сборкой.
- **Безопасность:** отдельный проход ревью на каждом этапе по правам доступа и утечке данных между файлами.

## 14. Риски

1. **Better Auth на Bun.** В документации примеры в основном для Node. Прототип этапа 1 проходит весь круг: письмо, подтверждение, одноразовость, сессия в Valkey, проверка сессии при открытии WebSocket. При провале — возврат к автору спеки с вариантами.
2. **Рост файлов с полной историей** (раздел 7.6): измеряется в этапе 3 на файле с 100 000 узлов.
3. **Разделение событий Loro и своего журнала отмены.** Обратные операции читают прежние значения из зеркала, поэтому оно должно обновляться раньше следующей своей правки. Проверяется тестом сходимости с отменой вперемешку с импортом.
4. **Память wasm в Worker сжатия:** ограничение размера документа и пересоздание Worker (раздел 7.4), замер на 100 000 узлах.
5. **TypeScript 7 и инструменты.** `vite` и `vite-plugin-solid` не используют `tsc` для сборки, но совместимость с E2E-проектом `tsconfig.e2e.json` проверяется в этапе 1.
